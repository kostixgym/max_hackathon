## 0. Объём: что сдаём

**Сдаём путь A целиком в демо-доме**, в мини-приложении и боте:
1. ссылка дома → подтверждение собственника → инициатива по шаблону → опрос в чате и в приложении;
2. требование в УК (PDF) → сотрудник УК создаёт собрание;
3. отметка бюллетеней → внесение решений → фиксация итога → протокол (PDF).

**В «Известные ограничения» README уходят:**
- путь B: сообщение о собрании, бюллетени с QR, ZIP;
- сканер QR, загрузка реестра;
- подтверждение собственника по телефону, по квитанции и через УК;
- напоминания, отметка «проголосовал онлайн», FAQ, свой вопрос;
- отмена инициативы и собрания;
- рассылка о просрочке требования: остаётся только флаг `overdue` при чтении.

**Честная оценка:**
- **Бэкенд не закончит всё 27-го.** Модуль собрания самый большой и занимает два дня, основная часть готова к вечеру 28-го.

**Создание собрания (Г2):**
- **Кто и когда:** сотрудник УК, который ведёт инициативу (`access.ManagesAsStaff`, решение 79: в демо-доме — только по
  своим инициативам), стадия `demand`, нет активного собрания.

- участники — учтённые бумажные бюллетени плюс ГИС;
- кворум — больше 50% площади;
- по каждому вопросу за / против / воздержался, принят по правилу типа решения (`rules.Passed`).

**Фиксация:**
- `meeting_results` пишется один раз;
- собрание переходит в `completed` с исходом `held` или `no_quorum`;

27-го).

**Готово, когда** интеграционный тест на PostgreSQL проходит сценарий «создать → получить бюллетени → завершить (демо) →
заполнить (демо) → предпросмотр → зафиксировать». Повторная фиксация — `409`, правку итога запрещает триггер.

**Тесты:**
- доли 1/2 и 1/3;
- кворум ровно 50% — нет кворума;
- ровно 2/3 — принято;
- воздержавшиеся при большинстве участников;
- не сотрудник — `403`; в демо-доме сотрудник по чужой инициативе — `403` (решение 79);
- правило 10 дней;
- решения до конца голосования — `409`.
- неполные или противоречивые результаты ГИС — `400`; ГИС до конца голосования и после фиксации — `409`;
- интеграционный сценарий ГИС + бумажный бюллетень на PostgreSQL 18.

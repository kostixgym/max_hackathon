# Изменения George

## HTTP API

- Все HTTP-маршруты перенесены под общий префикс `/api/v1`.
- Добавлено полное описание текущих и запланированных ручек:
  - `docs/API_DESCRIPTION.md` — формат запросов и ответов;
  - `docs/README-api-http.md` — назначение ручек, статус реализации и необходимые сущности БД.
- Сейчас реализованы следующие ручки:

| Метод и адрес | Назначение |
|---|---|
| `GET /api/v1/healthz` | Проверяет, что HTTP-процесс работает |
| `GET /api/v1/readyz` | Проверяет готовность сервиса и доступность PostgreSQL |
| `GET /api/v1/me` | Проверяет MAX `initData`, создаёт или находит пользователя и возвращает его данные и дом из `start_param` |
| `GET /api/v1/houses/{slug}` | Возвращает публичную информацию о доме и рассчитанные пороги голосования |
| `GET /api/v1/premises/{premiseID}/owners` | Возвращает доступный пользователю замаскированный список собственников помещения |
| `GET /api/v1/houses/{houseID}/meeting-officer-candidates` | Возвращает замаскированных кандидатов в председатели и секретари собрания |

- Для неизвестного маршрута и неподдерживаемого HTTP-метода добавлены единообразные JSON-ошибки.

## Переход на Gin

- Стандартный роутер `net/http` заменён на `Gin`.
- Gin используется только во входящем HTTP-слое `internal/platform/httpapi`.
- Авторизация MAX, логирование запросов и восстановление после panic перенесены в Gin middleware.
- Доменные модули и репозитории от Gin не зависят.
- `NewHandler` по-прежнему возвращает стандартный `http.Handler`, поэтому запуск сервера и HTTP-тесты остаются совместимыми с Go standard library.

## Ответ с информацией о доме

- В JSON-представление дома добавлено поле `id`.
- Поле возвращается как в `GET /api/v1/houses/{slug}`, так и внутри `house` ответа `GET /api/v1/me`.

## База данных и миграции

- Старая монолитная `00001_registry_access.sql` разделена на 23 последовательные goose-миграции:
  одна таблица — один файл с собственными секциями `Up` и `Down`.
- Сохранены 9 существовавших таблиц реестра и доступа и добавлены 14 таблиц остальных сценариев MVP:
  `decision_types`, `templates`, `template_items`, `initiatives`, `agenda_items`, `poll_votes`,
  `demands`, `meetings`, `ballots`, `ballot_decisions`, `gis_result_entries`, `meeting_results`,
  `audit_logs`, `registry_correction_requests`.
- Для новых HTTP-контрактов предусмотрены:
  - `Initiative.path` со значениями `A/B`;
  - `Ballot.status = online_declared` и `online_declared_at`;
  - причина и время отклонения `Membership`;
  - `RegistryUpload.applied_at`;
  - обращение «Данные неверны» с привязкой к пользователю, помещению, дому и версии реестра.
- Добавлены внешние ключи, проверки статусов, уникальность одного голоса собственника в опросе,
  одного бюллетеня на собрание и одного активного собрания на инициативу.
- `params_schema`, `ui_schema` и параметры инициатив хранятся в `jsonb`; веса голосов и результаты
  хранятся точными дробями без `float`.
- Добавлен тест, который проверяет порядок всех миграций, наличие единственных `Up/Down` и правило
  «одна таблица на файл». Интеграционный тест БД дополнен проверкой создания всех 23 таблиц.
- Модель данных и таблица готовности HTTP API синхронизированы с новой физической схемой.

Миграции переписаны до первого деплоя. Локальную базу, в которой уже применялась старая монолитная
`00001`, необходимо пересоздать. После первого деплоя изменять существующие файлы миграций нельзя —
любое изменение схемы должно добавляться новым номером.

## Менеджер транзакций

- В `internal/platform/db` добавлен `TransactionManager`, работающий напрямую через используемый
  проектом `pgx`: он открывает `pgx.Tx`, выполняет callback, делает `Commit` при успехе и `Rollback`
  при ошибке или panic.
- Ошибки callback возвращаются без замены, поэтому сервисы могут проверять доменные ошибки через
  `errors.Is`; ошибки открытия и фиксации транзакции получают дополнительный контекст.
- Добавлен интеграционный тест двух исходов: успешная запись сохраняется, а запись перед возвращённой
  ошибкой откатывается.

Правило для последующей разработки: **границу транзакции определяет сервис через
`TransactionManager.WithinTransaction`**. Все репозитории, участвующие в одной атомарной операции,
получают один и тот же `pgx.Tx`. Репозитории не должны самостоятельно вызывать `Begin`, `Commit` или
`Rollback`, а сервисы не должны открывать транзакции напрямую через пул. Вложенные вызовы менеджера
не используются: одна прикладная операция имеет одну верхнеуровневую транзакцию.

Менеджер обязателен, в частности, для создания инициативы вместе с повесткой, изменения инициативы
со сбросом голосов, выбора пути с созданием требования, создания собрания вместе с бюллетенями,
финализации результатов и записи `AuditLog` вместе с основным изменением.

## Привязки и собственники

- `GET /api/v1/me` теперь возвращает массив `memberships`: роль, статус, способ подтверждения, дом,
  помещение, долю и точный вес голоса пользователя.
- Добавлены защищённые списки собственников помещения и дома.
- ФИО физических лиц маскируется до формата `Фамилия И. О.`; телефон и полное ФИО через API не отдаются.
- Просмотр ограничен привязками пользователя и ролями сотрудников управляющей организации.

## Контракты будущего API

- `params_schema` зафиксирован как JSON Schema Draft 2020-12; настройки отображения вынесены в
  отдельный `ui_schema`.
- `allowed_actions` зафиксирован как список `{code, allowed, reason_code?}` с перечислением стабильных
  кодов действий и причин запрета.

### Новые контракты, пока только документация

В `docs/API_DESCRIPTION.md` добавлена явная иерархия двух разных процессов:

```text
предварительный опрос в MAX-приложении
├─ путь A → требование в УК → собрание организует УК
└─ путь B → без требования → собрание организует инициатор

официальное собрание
├─ онлайн-голосование в ГИС ЖКХ
└─ бумажный бюллетень как альтернативный канал
```

Для пути B отдельно расписана последовательность без участия УК: выбор `self-organize` → назначение
председателя и секретаря → создание собрания инициатором → голосование в ГИС ЖКХ → перенос агрегатов →
фиксация результата.

Добавлены контракты следующих ещё не реализованных ручек:

| Метод и адрес | Назначение |
|---|---|
| `POST /api/v1/initiatives/{id}/self-organize` | Выбрать путь B и перейти к самостоятельной организации собрания без УК |
| `PUT /api/v1/meetings/{id}/my-online-status` | Отметить «я проголосовал в ГИС ЖКХ» только для трекера и напоминаний |
| `POST /api/v1/memberships/{id}/data-correction-requests` | Отправить обращение «Данные неверны» по своей привязке |
| `GET /api/v1/meetings/{id}/my-ballots` | Получить список собственных бумажных бюллетеней и ссылки на скачивание |
| `GET /api/v1/ballots/{id}/pdf` | Скачать конкретный собственный бюллетень |

Отдельно зафиксировано, что `my-online-status` не принимает вариант голоса и не влияет на официальный
результат. Официальные агрегаты онлайн-голосования поступают через ГИС ЖКХ.

### Что потребуется реализовать в коде

Новые маршруты пока существуют только в документации и не зарегистрированы в Gin. Физическая схема
под них уже добавлена в отдельных миграциях.

Для приведения backend к новому контракту потребуется:

1. **Готово:** добавлены отдельные миграции для всех 23 таблиц MVP, включая `initiatives`, `demands`,
   `meetings`, `ballots`; в `ballots` есть статус `online_declared` и время отметки.
2. **Готово:** добавлена таблица `registry_correction_requests` с пользователем, привязкой, домом,
   помещением, версией реестра, причиной, комментарием, статусом и датами обработки.
3. Реализовать Go-структуры и репозитории на `pgx` для инициатив, собраний, бюллетеней и обращений об ошибках.
4. Реализовать сервисные проверки переходов пути B: вызывать может только подтверждённый
   собственник-инициатор; после пути A переход разрешён только при просрочке УК и отсутствии активного
   собрания.
5. При создании собрания формировать `Ballot` для каждого собственника из зафиксированной версии
   реестра. `my-online-status` должен изменять только бюллетени, доступные текущему пользователю.
6. Добавить генератор PDF одного бюллетеня и проверку, что запрашивающий пользователь связан с его
   `Owner` либо является администратором собрания.
7. Зарегистрировать новые Gin handlers, дополнить `allowed_actions` действием `select_path_b` и
   покрыть права доступа, переходы состояний и отсутствие влияния `online_declared` на итог тестами.

До выполнения этих шагов фронтенд не должен считать новые маршруты рабочими.

## Добавление TransactionManager

- В `backend/internal/platform/db/transaction_manager.go` добавлен менеджер транзакций на `pgx`.
- `WithinTransaction` открывает `pgx.Tx`, передаёт её в callback, выполняет `Commit` при успехе и
  `Rollback` при ошибке или panic.
- Ошибка callback возвращается без изменения, чтобы сервисы могли проверять доменные ошибки через
  `errors.Is`.
- Добавлен интеграционный тест, проверяющий сохранение записи после commit и отсутствие записи после
  rollback.
- Все последующие сервисы с несколькими связанными изменениями должны открывать транзакцию только
  через `TransactionManager` и передавать один и тот же `pgx.Tx` каждому участвующему репозиторию.
- Репозитории не должны самостоятельно вызывать `Begin`, `Commit` или `Rollback`. Вложенные вызовы
  `TransactionManager` также не используются: одна прикладная операция соответствует одной транзакции.

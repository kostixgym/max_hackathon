### Средние

| Проблема | Исправление |
|---|---|
| **В шаблоне не было процедурного вопроса.** Протокол называет председателя, секретаря и тех, кто считал голоса (Приказ Минстроя № 44/пр), а повестка их не избирала | Шаблон `video_surveillance` начинается с вопроса «Избрать председателя и секретаря общего собрания и наделить их полномочиями по подсчёту голосов», большинство участников (решение 74). Вторым идёт вопрос о видеонаблюдении, 2/3 от всех |
| **Не было лимита на размер тела запроса**, большой JSON целиком читался в память | Не больше 64 КБ: по `Content-Length` сразу `413 request_too_large`, тело без длины обрезается через `http.MaxBytesReader` |
| **Персональные данные в очереди хранились вечно**: в `payload` лежит MAX id получателя | Воркер раз в минуту удаляет выполненные и проваленные задачи старше 30 дней (решение 75) |
| **В приглашении не было срока опроса и пути в приложение** | «Опрос идёт до 3 октября, 18:00» по времени дома и кнопка «Открыть приложение» с домом опроса |

Сознательно не сделано:
- **Возврат застрявших после падения джоб только через 10 минут.** Это компромисс: порог не даёт отнять джобу у живого
  воркера на другом инстансе.
- **Составные внешние ключи «собственник ↔ квартира» и «вопрос ↔ собрание».** Сейчас эти связи держит код. Ключи добавим
  вместе с модулем собрания, когда появятся таблицы, которые их используют.

### Найдено по ходу и исправлено

- **`Claim` мог забрать больше джоб, чем просили.** Запрос `UPDATE … WHERE id IN (SELECT … LIMIT n FOR UPDATE SKIP LOCKED)`
  — известная ловушка PostgreSQL: при плане с вложенным циклом подзапрос выполняется несколько раз, каждый раз пропуская
  уже заблокированные строки. Интеграционный тест поймал `Claim(1)` → 3 джобы. На SQL это воспроизведено: при запрете
  хеширования и материализации старый запрос с `LIMIT 1` забирает 3 строки. Теперь выбор идёт через
  `WITH picked AS MATERIALIZED (…)`, такой CTE выполняется ровно один раз.
- **Снимок реестра брался при создании черновика, а решение 2 требует брать его при запуске опроса.** Если реестр
  перезальют между созданием и запуском, опрос считался бы по устаревшей версии. `StartPoll` теперь переводит инициативу
  на текущую применённую версию.

## API по контракту

| Было (шаг 1.1) | Стало (контракт) |
|---|---|
| `POST /initiatives`, дом в теле | `POST /houses/{houseID}/initiatives`. Поле `params` сохраняется, в ответе есть `registry_version` и `agenda_items` |
| `start-poll` с `days` | `start-poll` с `ends_at` (RFC 3339), от часа до 30 дней; без тела — 7 дней |
| `GET /initiatives/{id}/progress` | `GET /initiatives/{id}/poll` с полями `for_m2`, `against_m2`, `total_m2`, `demand_m2`, `demand_reached`, `poll_ends_at` и дополнительными для дашборда |
| голос только кнопками в чате | плюс `PUT /initiatives/{id}/my-vote` с анкетой. Без полей анкеты сохранённые ответы остаются, «против» их сбрасывает |
| шаблон `cctv` | шаблон `video_surveillance` |
| — | `POST /houses/{slug}/demo-membership` описан в контракте как ярлык демо-дома |

Прогресс видят подтверждённые жители дома и сотрудники его УК (решения 19 и 43).

Двухшаговая привязка через `/memberships`, `GET /templates`, список инициатив дома и карточка инициативы с `allowed_actions`
в контракте есть, но пока не реализованы. Они понадобятся вместе с экранами мини-приложения.

## Решения и почему

| Решение | Почему |
|---|---|
| **Приглашение в демо-доме — только инициатору**, а не отдельный демо-дом на каждого тестировщика | Одно правило в рассылке закрывает спам и не меняет модель. Опрос по-прежнему проверяется целиком: инициатор получает сообщение и голосует. Голоса других тестировщиков можно проверить через `my-vote` |
| **Лимит — 10 инициатив в сутки на пользователя**, а не лимит частоты запросов | Злоупотребить можно именно рассылкой, а её запускает только инициатива. Простой счётчик в той же транзакции, что и создание, внешний компонент не нужен |
| **Тихие часы считаются при постановке задачи**, а не при отправке | Время запуска известно, `run_at` просто ставится на 9:00. Воркеру не нужно откладывать задачи и тратить попытки. Часы клиента и базы при этом не сравниваются: днём `run_at` — это `now()` базы |
| **Сообщение перестраивается из `Polling` и дома заново**, а не хранится | Решение 68 разрешает обновлять сообщение без его id. Текст всегда отражает текущую стадию: после конца опроса кнопки исчезают |
| **Триггер сравнивает строки итога целиком без `finalized_by`** (`to_jsonb(NEW) - 'finalized_by'`) | Разрешено ровно одно изменение. Новая колонка в таблице итогов автоматически попадает под запрет |
| **`ends_at` вместо `days`** | Так в контракте, и инициатор может выбрать точное время конца, например воскресенье, 18:00 (решение 18) |

## Как проверено

- `gofmt`, `go vet`, все тесты с `-race` на PostgreSQL 18. Три прогона подряд на одной базе, в том числе с посторонними
  задачами в очереди.
- **Новые тесты:**
  - тихие часы: границы 21:59, 22:00, 08:59, 09:00, переход через полночь, другой часовой пояс;
  - отбор адресатов в демо-доме;
  - кривые id и пустой заголовок — без запросов к базе;
  - обслуживание очереди: возврат застрявших джоб и удаление старых;
  - бот:
    - приглашение с тремя строками кнопок и сроком по местному времени;
    - обновление сообщения после голоса;
    - после конца опроса кнопки голосования исчезают;
  - HTTP: ручки контракта, `my-vote` с анкетой и ошибками, `ends_at` вне допустимого срока, 413, 429;
  - база: удаление пользователя, зафиксировавшего итог, проходит, а правка итога вместе с обнулением `finalized_by` — нет;
  - интеграционный тест опроса:
    - процедурный вопрос первым и сохранённые `params`;
    - приглашение только инициатору, `run_at` по тихим часам;
    - снимок при запуске опроса;
    - лимит 10 инициатив;
    - удаление джоб старше 30 дней.
- **Смоук собранного бинарника:**
  - демо-подтверждение, затем инициатива по пути контракта: повестка из двух вопросов, `registry_version: 1`;
  - `start-poll` с `ends_at`;
  - джоба приглашения стоит на «сейчас», потому что проверка шла днём;
  - `my-vote` с анкетой возвращает 63,50 м²;
  - `/poll` отдаёт поля контракта;
  - запрос больше 64 КБ получает 413, старые пути — 404;
  - ошибок в журнале нет.
- Сквозной тест бота на поддельном MAX проверяет, что ответ на нажатие несёт обновлённое сообщение с выбором и весом.

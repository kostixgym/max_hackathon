# Правки по ревью этапа 0: мажорные замечания

Дата: 26.09.2026. Статус: готово, ждёт ревью. Ветка: `fix/review-stage-0`.

Ревью всего кода этапа 0 (`go-review`, ветка `chore/docker-ci` относительно `main`) нашло три мажорных замечания.
Здесь — их исправление. Мелкие замечания собраны в конце и пойдут отдельным шагом. Миграций в шаге нет,
пересоздавать локальную базу не нужно.

## Что сделано

### 1. Бот молчит в групповых чатах

**Было.** На любое сообщение бот отвечал подсказкой и не проверял тип чата. Если УК добавит бота в домовой чат
(решение 44), он будет отвечать на каждую реплику соседей.

**Стало.** Бот отвечает только в личном диалоге (`recipient.chat_type = dialog`). В группах и каналах он молчит,
даже на `/start`. Если тип чата не пришёл, тоже молчит. Вход по ссылке дома не затронут: `bot_started` приходит
только из личного диалога.

```
backend/internal/bot/bot.go        проверка типа чата у message_created
backend/internal/bot/bot_test.go   группа, /start в группе, канал, пустой тип чата
backend/cmd/app/bot_e2e_test.go    сообщение из группового чата в JSON, как его присылает MAX
```

Сквозной тест нужен, чтобы проверить не только обработчик, но и официальный клиент: он должен класть `chat_type`
из JSON туда, откуда его читает бот.

### 2. Нет записи в БД на каждом запросе API

**Было.** `UpsertUser` выполнял `INSERT … ON CONFLICT DO UPDATE` на каждом запросе. Любое чтение становилось записью:
новая версия строки, WAL, «мёртвые» строки для VACUUM, блокировка строки, на которой параллельные запросы одного
пользователя ждали друг друга.

**Стало.** `EnsureUser`: сначала `SELECT` по уникальному индексу `max_user_id`. Записываем только при первом входе,
через `INSERT … ON CONFLICT DO NOTHING`. Если два первых запроса пришли одновременно, проигравший получает пустой
результат и читает строку победителя.

```
backend/internal/access/store.go                     EnsureUser вместо UpsertUser
backend/internal/platform/httpapi/auth.go            интерфейс Users
backend/internal/access/access_integration_test.go   TestEnsureUser
```

**Уточнение к ревью.** В ревью я написал, что игнорируется `deleted_at` и удалённый аккаунт «воскреснет». Это
неточно. По схеме удаление аккаунта — это удаление строки: у привязок и голосов опроса `ON DELETE CASCADE`,
у остальных ссылок `SET NULL`, что ровно повторяет решение 28. Вернувшийся пользователь получит новый аккаунт.
Колонка `users.deleted_at` нигде не используется, про неё — в разделе «Найдено по ходу».

### 3. Модули читают чужие данные только через интерфейсы

**Было.** Модуль `access` в 17 местах читал таблицы реестра (`premises`, `houses`, `owners`, `owner_records`,
`registry_uploads`) и инициатив (`initiatives`) напрямую. Это нарушало принцип 8 из 04, и в этапе 1 по этому
образцу написали бы остальные модули.

**Стало.**

```
backend/internal/registry/read.go         API чтения для других модулей: House, Premises, PremiseOwners, HouseOwners, Owners
backend/internal/initiatives/store.go     новый модуль «Инициативы»; пока один метод IsPathBInitiator
backend/internal/access/store.go          интерфейсы Registry и Initiatives; SQL только по users, memberships, org_members
backend/cmd/app/main.go                   связывание модулей
backend/migrations/ownership_test.go      проверка владения таблицами
```

- **`registry`** отдаёт дом, помещения и собственников текущей версии реестра. SQL по таблицам реестра теперь
  только в этом пакете.
- **`access`** решает, кто что видит: собственников квартиры видит подтверждённый житель или собственник этой
  квартиры и сотрудник УК, кандидатов в председатели — только организатор собрания. Нужные данные `access`
  получает через объявленные им интерфейсы. Контракт API не изменился: JSON прежний.
- **`ownership_test.go`** проверяет принцип 8 автоматически. У каждой таблицы из миграций ровно один модуль-владелец,
  карта повторяет таблицу из 04. SQL в не-тестовом коде модуля называет только его таблицы. Пакеты `platform` и
  `bot` таблиц не касаются. Правило и пример записаны в 05 («Структура репозитория») и в принципе 8 в 04.

Заодно закрыты два nit из ревью. SQL больше не собирается из фрагмента `where`: запросы в `registry` составлены
только из констант. Непонятное имя `houseOwnerAccess` заменено на `organizesMeeting`.

## Решения и почему

| Решение | Почему |
|---|---|
| **Бот отвечает только при `chat_type = dialog`**, при неизвестном типе молчит | Голосование и напоминания — только в личке (решение 44), анонсы в домовом чате придут позже с `HouseChat`. Промолчать безопаснее, чем заспамить чат соседей |
| **`DO NOTHING` и повторное чтение вместо `DO UPDATE`** | `DO UPDATE` пишет строку даже при конфликте, а `DO NOTHING` при конфликте ничего не пишет. Гонку двух первых запросов закрывает повторное чтение |
| **Интерфейс объявляет модуль, которому нужны данные** (`access.Registry`), реализует владелец (`registry.Store`) | `access` зависит от нужных ему методов, а не от реализации реестра. Реестр ничего не знает про `access`, циклов между пакетами нет. Связывание в одном месте — `main.go` |
| **Маскирование ФИО осталось в `access`**, реестр отдаёт полное ФИО | Что показывать пользователю, решает модуль доступа. Протоколу собрания на этапе 2 понадобятся полные ФИО из того же API реестра |
| **Некорректный id из URL отсекается в `access` до запросов** | Как и раньше: сразу 404, без обращения к БД |
| **Карточки «Мой дом» сортируются в Go** | Адрес и номер квартиры — данные реестра: `ORDER BY` по ним в SQL модуля `access` снова означал бы `JOIN`. Порядок прежний: адрес, номер, id |
| **Проверка владения ищет в SQL `FROM`, `JOIN`, `INTO`, `UPDATE`** перед именем таблицы | Простая эвристика без разбора SQL. Ключевые слова у нас всегда заглавные, поэтому английский текст в комментариях её не сбивает. Тестовые файлы не проверяются: фикстурам можно заполнять любые таблицы |
| **Цена границ модулей:** `/me` делает до 4 коротких запросов по индексам, проверка доступа к кандидатам — до 5 | Раньше `/me` делал запись и `JOIN`. Для экранов, которые открывают раз в сессию, разница незаметна. Если экран станет горячим, для него заведут модель чтения внутри модуля-владельца, а не `JOIN` по чужим таблицам |

## Как проверено

- `gofmt`, `go vet` и все тесты, включая интеграционные на PostgreSQL 18. Два прогона подряд на одной базе,
  чтобы убедиться, что тесты повторяемы.
- **Новые тесты ловят исходные проблемы.** Каждую правку временно откатывал и запускал тесты:
  - без проверки `chat_type` падают юнит-тесты бота и сквозной тест;
  - со старым `DO UPDATE` падает `TestEnsureUser`: `xmin 861 -> 862`, то есть строку известного пользователя
    перезаписали;
  - на старом `access/store.go` тест владения находит все 17 обращений к чужим таблицам.
- **Интеграционные тесты `access`:**
  - прежние 12 сценариев доступа;
  - 404 для неизвестных дома и квартиры;
  - «Мой дом» по данным двух модулей: отозванная привязка скрыта, у гостя нет данных собственника;
  - второй вход не меняет строку пользователя;
  - 8 параллельных первых входов дают одного пользователя.
- **Смоук собранного бинарника** на PostgreSQL 18 с `DEV_MODE`:
  - `/me` с привязкой собственника: демо-дом, кв. 12, 63.50 м², «Васильев Д. П.»;
  - собственники квартиры — 200;
  - кандидаты в председатели для собственника без инициативы — 403;
  - неизвестный и некорректный id — 404;
  - ошибок в журнале нет.
- Образ бэкенда собирается за 8 секунд.

## Найдено по ходу

- **Удаление аккаунта упадёт на итогах собраний.** У `meeting_results.finalized_by` стоит `ON DELETE SET NULL`, а
  триггер «записывается один раз» запрещает любой `UPDATE`. Поэтому удаление пользователя, который фиксировал итог,
  падает с ошибкой `meeting_results rows are write-once: UPDATE is not allowed` (воспроизведено на PostgreSQL 18).
  Удаления аккаунта в коде ещё нет, поэтому сейчас ничего не сломано. Исправить до реализации решения 28 новой
  миграцией: триггер должен разрешать единственное изменение — обнуление `finalized_by`.
- **Колонка `users.deleted_at` не используется** и противоречит схеме: внешние ключи рассчитаны на удаление строки.
  Её стоит убрать в той же миграции. Если решим делать удаление мягким, понадобятся другие правила уникальности
  `max_user_id`.

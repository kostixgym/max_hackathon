# Шаг 1.1. Опрос поддержки в боте: очередь, рассылка, голосование кнопками

Дата: 26.09.2026. Статус: готово, ждёт ревью. Ветка: `feat/poll-bot` (от `fix/review-stage-0`).

Цель шага — первая половина сквозного сценария этапа 1: собственник создаёт инициативу по шаблону,
запускает опрос, бот рассылает сообщение с кнопками «Поддерживаю / Против / Есть вопрос», голос
учитывается в м² по снимку реестра, а инициатор видит прогресс. Собрание, требование и PDF — следующие шаги.

### Миграции
- `jobs`: тип, JSONB-payload, `dedup_key` (UNIQUE — повторный запуск опроса не дублирует сообщения),
  статусы queued/running/done/failed, попытки, `run_at`. Индекс `(status, run_at)` под поллинг очереди.
- `bot_markers`: `(bot_user_id, marker)`. Владелец обеих таблиц — модуль `notify`
  (обновлены `ownership_test` и карта владения).

### Очередь и воркер (`notify`)
- Клейм пачки: `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED)` — несколько воркеров
  не берут одну джобу.
- Ошибка → повтор с паузой 1 → 5 → 30 минут (docs/03, вкладка 5C), исчерпание попыток → `failed`.
- На старте воркер возвращает в очередь джобы, застрявшие в `running` после падения (10 минут).
- `run_at` по умолчанию берётся из `now()` базы: часы клиента, убежавшие вперёд, не откладывают джобу
  в будущее (нашли на живом прогоне — контейнер БД отставал от хоста).
- Этап 1: воркер работает в том же процессе, что и API (docs/03, вкладка 5D). Запускается вместе с ботом:
  без токена рассылать некому, джобы ждут в очереди.

### Запуск опроса (`initiatives.StartPoll`)
- Одна транзакция через `TransactionManager`: `draft → poll` + джобы `poll_invite` на каждого
  подтверждённого собственника (получатели — модуль `access`, он знает и MAX id).
- Снимок реестра фиксируется при создании инициативы (`CurrentSnapshot`): пороги и веса не поплывут
  при перезаливке реестра (docs/04, принцип 3).
- Повестка создаётся из пунктов шаблона; типы решений и их id приходят из каталога `rules` —
  модуль инициатив не читает чужие таблицы (проверяет ownership-тест).

### Голосование (`poll.CastVote`)
- Голос привязан к собственнику, вес копируется из `OwnerRecord` снимка и больше не меняется (решение 54).
- Несколько помещений у одного пользователя → по строке голоса на каждую долю, веса суммируются
  (docs/01, «Особые случаи»).
- Смена голоса «за» → «против» сбрасывает анкету (инвариант 7); CHECK в таблице дублирует правило.
- Прогресс считается на лету (решение 65): суммы точными дробями, пороги от общей площади снимка,
  `demand.reached` — набрано ли 10% для требования УК.
- Ошибки домена различимы: не собственник, опрос закрыт, собственника нет в снимке.

### Бот
- Рассылка: заголовок, адрес дома, явная пометка «не является голосованием собрания и юридической силы
  не имеет», кнопки-callback `pv:<initiative>:<for|against|question>`.
- Нажатие: `EnsureUser` → `CastVote` → ответ пользователю через `AnswerOnCallback` (POST /answers,
  решение 68 — без хранения id сообщения): «Голос учтён: 26,15 м² „за“ (кв. 45)» или причина отказа.
- Поллер грузит маркер из БД на старте и сохраняет после полностью обработанной пачки: перезапуск
  не теряет и не дублирует события (рекомендация ревью 0.3; обработчики идемпотентны —
  at-least-once безопасен).

### API (Gin, `/api/v1`)
| Метод | Доступ | Что |
|---|---|---|
| `POST /houses/:house/demo-membership` | аутентификация | подтверждение собственника в демо-доме (`owner_index` для квартир с сособственниками) |
| `POST /initiatives` | подтверждённый собственник дома | инициатива из шаблона (201) |
| `POST /initiatives/:id/start-poll` | инициатор | запуск опроса + рассылка |
| `GET /initiatives/:id/progress` | подтверждённый житель дома | прогресс в м², %, пороги, `demand.reached` |

### Связывание
`access` остаётся без обратной зависимости: интерфейс получателей объявлен в `initiatives`
(тип `Recipient` живёт там), реализован `access`. Цикла импортов нет, владение таблицами не нарушено.

## Как проверено

```
go vet ./... && go test ./...                     # юнит: bot (колбэки), httpapi (4 эндпоинта), e2e с фейк-MAX
TEST_DATABASE_URL=… go test ./... -count=1        # интеграция на PostgreSQL 18
go test ./... -race -count=1                      # без гонок
```

- **E2E с фейк-MAX** теперь покрывает и голосование: `bot_started` → приветствие с кнопкой;
  `message_callback` с `pv:…:for` → голос записан, `POST /answers` получил «Голос учтён … 26,15»,
  маркер 8 сохранён.
- **Интеграционный тест флоу**: демо-подтверждения трёх собственников (кв. 43 — две доли 1/2,
  кв. 7 — доля 1/3), конфликт двух аккаунтов на одной записи (инвариант 9), создание инициативы,
  `StartPoll` только инициатором, 3 джобы `poll_invite`, голоса 24+16 м² «за», смена голоса со сбросом
  анкеты, 16/48 м² после смены, отказ не-собственнику, заморозка опроса, дедуп и жизненный цикл
  джобы (done / failed), маркеры, идемпотентность сида каталога.
- **Живой смоук** на PostgreSQL 18 с `DEV_MODE`: healthz → демо-подтверждение кв. 43 → создание
  инициативы «cctv» → запуск опроса (7 дней) → прогресс 3000/300/1500/2000 от снимка; джоба
  `poll_invite` в очереди (воркер без токена не стартует — ждёт, как задумано).

## Решения и почему

| Решение | Почему |
|---|---|
| **`run_at` из `now()` базы, а не клиента** | Часы клиента/хоста и БД в разных контейнерах расходятся; джоба с «будущим» run_at молча не берётся. Нашено на живом прогоне |
| **Маркер сохраняется после пачки, а не после каждого апдейта** | At-least-once вместо at-most-once: повторная обработка безопасна (голос — upsert), а потерянный хвост пачки означал бы потерянные голоса |
| **`owner_index` в демо-подтверждении** | В квартире с сособственниками два тестировщика должны получить разные записи — иначе упираются в инвариант 9. Для жюри: пары «кв. 43, собственник 1/2» |
| **Джобы по одной на получателя с `dedup_key`** | Рестарт воркера или повторный запуск не спамит; лимиты MAX API соблюдаются по одной отправке на джобу |
| **Тип `Recipient` объявлен в `initiatives`, реализация в `access`** | Разрывает цикл импортов: каждому модулю нужен только интерфейс соседа |
| **Каталог (`DecisionType`, шаблоны) сидируется при `SEED_DEMO`** | Правит только платформа (решение 9); сид идемпотентен, повторный старт ничего не меняет |
| **Прогресс без таблицы-агрегата** | Решение 65: на 60–200 помещениях суммы на лету дешевле поддержки синхронности; PollTally — при масштабировании |

## Что не сделано в этом шаге

- Напоминания об окончании опроса и итог опроса в чат — с модулем `meeting` (таймер по `poll_ends_at` уже есть).
- Жители-несобственники не получают информационное сообщение при запуске опроса (по 02, шаг 2) —
  следующий шаг вместе с `shareMaxContent`.
- Анкета («как удобнее голосовать», «готов помочь») задаётся только параметрами API; экран в
  мини-приложении — за фронтендом (0.4).
- `AuditLog` шага ещё не пишет (модуль журнала не написан) — событие «запуск опроса» попадёт туда
  вместе с реализацией журнала.
- Воркер и поллер в одном процессе; разделение (роль `worker`) — этап 2 по docs/03.

## Вопросы на ревью

1. `CastVote` берёт стадию инициативы без блокировки строки: теоретически голос может проскочить
   в момент заморозки опроса. Закрывать через доменное событие или оставить (голос не юрсилен)?
2. Джобы `poll_invite` не перепланируются на новых собственников, подтверждённых после запуска опроса —
   они смогут проголосовать, но не получат сообщение. Приемлемо для MVP или добавить «догоняющую» джобу?
3. `owner_index` — достаточно ли для демо, или сразу делать выбор по маскированному ФИО?

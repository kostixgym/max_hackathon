# Шаг 0.3. Бот: получение событий, `/start`, кнопка мини-приложения

Дата: 25.09.2026. Статус: готово, ждёт ревью. Ветка: `feat/bot-start`.

Цель шага — бот, который отвечает в MAX и одной кнопкой открывает мини-приложение, причём сразу в нужном доме, если человек
пришёл по ссылке дома. Голосование кнопками в чате, напоминания и «Поделиться номером» — этап 1.

## Что сделано

```
backend/
  internal/platform/maxbot/poller.go       цикл long polling: marker, повтор при ошибках, изоляция паник (+ тест)
  internal/bot/bot.go                      обработчики: bot_started, /start, прочие сообщения (+ тест)
  cmd/app/main.go                          runBot: запуск бота рядом с HTTP API, корректная остановка
  cmd/app/bot_e2e_test.go                  сквозной тест с поддельным MAX API
```

### Поведение бота

| Событие | Ответ |
|---|---|
| `bot_started` со ссылкой дома (`max.ru/<бот>?start=<invite_slug>`) | приветствие с адресом дома (для демо-дома — пометка «данные синтетические») + кнопка «Открыть приложение», которая передаёт дом в мини-приложение |
| `bot_started` без ссылки, с неизвестным домом или с недопустимым `payload` | общее приветствие: что умеет приложение, «откройте ссылку или QR-код от вашей УК» + кнопка без дома |
| сообщение `/start` или `/start <invite_slug>` | то же, что `bot_started` |
| любое другое сообщение | короткая подсказка «все действия — в приложении» + кнопка |
| сообщения от ботов, прочие события | игнорируются |

### Как дом попадает в мини-приложение
Кнопка `open_app` содержит `payload = invite_slug`, MAX передаёт его в мини-приложение как `start_param`. Дальше работает то,
что сделано в 0.2: `/api/me` читает `start_param` из **подписанного** `initData` и отдаёт сводку дома. Второй путь без бота —
прямая ссылка `max.ru/<бот>?startapp=<invite_slug>` (в 0.2).

### Цикл получения событий (`platform/maxbot`)
- Long polling через `Subscriptions.GetUpdates` официального клиента, `marker` сдвигается только после успешного ответа.
- Таймаут без событий — норма, запрос повторяется сразу.
- Сетевые ошибки и ошибки MAX — повтор с паузой от 1 до 30 секунд, растущей вдвое.
- Паника в обработчике одного события логируется и **не останавливает бота**.
- События обрабатываются по одному, по порядку: так сохраняется порядок действий каждого пользователя.

### Запуск (`runBot` в `main.go`)
- Бот запускается, только если задан `MAX_BOT_TOKEN`.
- Получает свой id и имя (`GetMyInfo`) с повтором каждые 5 секунд: без них нельзя собрать кнопку `open_app`.
- Если у бота есть webhook-подписки, пишет предупреждение: при них long polling не получает событий.
- Проблемы с MAX API **не роняют сервис**: HTTP API мини-приложения работает независимо.
- При остановке (`SIGTERM`) сервис дожидается завершения бота.

## Решения и почему

| Решение | Почему |
|---|---|
| **Бот — отдельные пакеты: цикл в `platform/maxbot`, обработчики в `bot`** | Цикл — инфраструктура (зона Платформы), обработчики — сценарии (зона «Вход в продукт»). Их можно менять независимо, и обработчики тестируются без сети |
| **Кнопка `open_app` собирается вручную (`model.Button`), а не хелпером `AddOpenApp`** | Хелпер клиента не умеет передавать `payload`, а без него дом не попадёт в мини-приложение. Поля взяты из схемы API в клиенте: `web_app` — имя бота, `contact_id` — его id, `payload` — `^[\w-]{0,512}$` |
| **`payload` проверяется тем же шаблоном до поиска дома** | Строку, которую MAX не примет в кнопке, мы не отправляем. Наш `invite_slug` (base64url) шаблону соответствует |
| **Адрес дома — в приветствии, персональных данных нет** | Ссылка дома публичная (решение 57), адрес и так на подъезде |
| **Long polling, а не webhook** | Боту не нужен публичный адрес, локальный запуск работает без туннелей. Для роста на этапе 3 — webhook (docs/05) |
| **Ошибки MAX — повторы, а не падение** | Если MAX недоступен при старте, API мини-приложения не должен становиться недоступным вместе с ним |
| **Сквозной тест с поддельным MAX API** | Юнит-тесты проверяют обработчик, но не то, что официальный клиент реально отправляет. Сквозной тест поднимает `httptest`-сервер вместо MAX и проверяет: токен в `Authorization`, ответ в нужный чат, JSON кнопки (`open_app`, `payload`, `web_app`, `contact_id`), `marker` в следующем запросе |

## Как проверено

```
cd backend
go vet ./...                 # без замечаний
go test ./...                # + bot, maxbot, cmd/app (сквозной) — ok
TEST_DATABASE_URL=... go test ./... -count=1   # все пакеты, включая интеграционные — ok
```

- `poller_test`: порядок обработки, `marker` только после успеха (0 → 10 → 10 → 10 → 11), таймаут без паузы, повтор после сетевой ошибки, паника в обработчике не останавливает цикл, остановка по отмене контекста.
- `bot_test`: приветствие с адресом и `payload` для известного дома; общее приветствие без `payload` — без ссылки, для неизвестного дома, для недопустимого `payload`, для `/start`; `/start <slug>`; подсказка на прочие сообщения; игнор ботов и прочих событий.
- `bot_e2e_test`: полный путь через официальный клиент и поддельный MAX API, см. таблицу решений.

**В настоящем MAX не проверено: нет токена.** Это шаг 0.6.

## Что не сделано и что нужно для проверки на токене

- **Адрес мини-приложения в настройках бота** на платформе MAX («Чат-боты → Настройки»): без него кнопка `open_app` откроет пустоту. Адрес появится после деплоя с HTTPS (шаг 0.5). Добавить в README.
- **Проверить на токене (0.6):** доходит ли `payload` кнопки до `start_param` мини-приложения; работает ли `max.ru/<бот>?start=<slug>` → `bot_started` с `payload`.
- Кнопки голосования (`message_callback`), «Поделиться номером», рассылки и напоминания — этап 1.
- Команды бота в меню (`PatchCommands`) — не нужны, пока команда одна.

## Про ветку

Ветка `feat/bot-start` стоит поверх `feat/backend-skeleton` (PR #1), в которую влиты изменения Георгия
(`docs/completed/georgechanges.md`: Gin и `/api/v1`, 23 миграции, `TransactionManager`, привязки и каталоги собственников).

После слияния PR #1 (squash) перенести ветку на `main`:

git fetch origin

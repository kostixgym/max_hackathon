## Реализованный API

### Запрос

```http
PUT /api/v1/meetings/{id}/gis-results
Content-Type: application/json
```

```json
{
  "entries": [
    {
      "agenda_item_id": "0199...",
      "for_m2": "1800.00",
      "against_m2": "100.00",
      "abstain_m2": "50.00"
    }
  ],
  "online_participants_m2": "1950.00"
}
```

### Правила

- ручка доступна только администратору собрания;
- собрание должно иметь форму `gis_electronic`;
- данные принимаются только после окончания голосования;
- площади передаются строками и считаются точно, без `float64`;
- разрешены неотрицательные значения с точностью до двух знаков после точки;
- нужны результаты по всем вопросам повестки без дублей;
- по каждому вопросу сумма «за + против + воздержался» должна совпадать с площадью онлайн-участников;
- площадь онлайн-участников не может превышать площадь снимка реестра;
- повторный `PUT` исправляет данные до финализации;
- после финализации возвращается `409 already_finalized`.

Добавлены коды ошибок:

- `400 invalid_gis_results`;
- `409 gis_results_not_allowed`;
- используются существующие `403 staff_only`, `404 meeting_not_found`, `409 voting_not_finished` и
  `409 already_finalized`.

## Домен и база данных

Добавлен `backend/internal/meeting/gis.go`:

Новая миграция не понадобилась: нужная таблица и поля уже были в схеме.

Запись выполняется одной транзакцией. Строка собрания блокируется `FOR UPDATE`, поэтому ввод ГИС согласован с
одновременной финализацией: `Finalize` получает полный набор данных, а поздняя правка не проходит.

## Подсчёт результата

Функция `tally` расширена официальными агрегатами ГИС:

```text
участники = online_participants_m2 + веса учтённых бумажных бюллетеней

голоса по вопросу = агрегаты ГИС + решения бумажных бюллетеней
```

После объединения теми же функциями `rules.QuorumReached` и `rules.Passed` рассчитываются кворум и принятие каждого
вопроса. Все вычисления используют `math/big.Rat`.

`Preview` читает оба источника. `Finalize` после блокировки повторно читает оба источника внутри своей транзакции и
записывает объединённый неизменяемый итог в `meeting_results`. `ProtocolData` автоматически получает уже объединённые
данные из зафиксированного результата.

## HTTP-слой

Изменены:

- интерфейс `Meetings`;
- handler `meetingGISResults`;
- DTO запроса и ответа;
- точный парсер площади;
- отображение доменных ошибок в API;
- регистрация маршрута в `server.go`;
- проверка заглушки `501`, если модуль собрания не подключён.

Парсер принимает `0`, `0.00`, `1950.5`, `1950.50` и отвергает отрицательные числа, экспоненты, дроби, пробелы,
`NaN`, слишком большую точность и значения, не помещающиеся в БД.

## Результаты проверок

Успешно выполнены:

```text
go vet ./...
go test ./internal/meeting ./internal/platform/httpapi -count=1
go test ./migrations ./internal/meeting ./internal/platform/httpapi -count=1
go test -p 1 ./... -count=1 -timeout 5m
```

Полный последовательный прогон выполнялся на PostgreSQL 18 с `pool_max_conns=2` и прошёл целиком.

Обычный параллельный `go test ./...` остаётся нестабильным из-за существующей взаимной работы интеграционных пакетов
с одним демо-домом и нестабильного `notify/TestWorkerCompletesAndRetries`. Отдельные и последовательные прогоны этих
пакетов проходят. Это не связано с логикой Г8, но может потребовать повторного запуска CI.

Локальный `-race` на Windows не запустился: отсутствует CGO/GCC. В CI проект запускает `-race` на Linux.

Временный контейнер PostgreSQL 18 после тестов удалён.

# Собрание, Г4–Г7: решения, итог, демо-ускорители, данные для протокола

Дата: 27.09.2026. Статус: влито (PR #9, `6477ebf`). Ветка: `feat/meeting-result` (от `main` после PR #8 с Г1–Г3).

Вторая половина задач Гоши из [плана до 30.09](../plan-do-30-09.md). Вместе с [Г1–Г3](sobranie-g1-g3.md) модуль
собрания закрывает путь A от создания собрания до зафиксированного итога. Последующее Г8 с итогами ГИС выполнено
отдельно: [отчёт Г8](sobranie-g8.md).

## Что сделано

### Г4. Решения по бюллетеню — `PUT /ballots/{id}/decisions`

- Только администратор собрания и только **после окончания голосования** (решение 26: во время голосования
  отмечается лишь «бюллетень получен»).
- Бюллетень должен быть получен до окончания, иначе **новый код `409 ballot_not_received`**: опоздавший бюллетень не
  учитывается.
- Решения — ровно по одному на каждый вопрос повестки, иначе `400 invalid_request`.
- Повторная отправка до фиксации итога исправляет ошибку: решения заменяются.
- В транзакции строка собрания блокируется `FOR SHARE`. Бюллетени вносятся параллельно, а фиксация итога ждёт, пока
  они запишутся.

### Г5. Итог

- **Подсчёт — чистая функция `tally`:**
  - участники — владельцы учтённых бюллетеней;
  - кворум — больше 50% площади дома (`rules.QuorumReached`);
  - вопрос принят по правилу своего типа решения (`rules.Passed`) и только при кворуме;
  - суммы точные: доли 1/3 не округляются.
- **`GET /meetings/{id}/result-preview`** — для администратора, до фиксации.
- **`POST /meetings/{id}/finalize`** — одна транзакция:
  - строка собрания `FOR UPDATE`;
  - подсчёт по той же транзакции;
  - строки `meeting_results` по каждому вопросу, их потом не изменить из-за триггера;
  - собрание → `completed` с `outcome` (`held` или `no_quorum`) и площадью участников;
  - инициатива → `completed`;
  - задача `meeting_finalized` для бота.
- **Два одновременных нажатия** дают один итог, второе получает `409 already_finalized`. После фиксации решения,
  демо-ускорители и повторная фиксация отвечают тем же кодом.

### Г6. Демо-ускорители — только демо-дом, только администратор

- **`finish-voting`** ставит конец голосования на «сейчас». Сообщение и начало голосования, если они ещё впереди,
  сдвигаются в прошлое, чтобы соблюдался порядок дат в таблице.
- **`fill-ballots`** — только после окончания голосования:
  - в порядке трекера отмечает полученными и учтёнными бюллетени, пока участники не наберут 80% площади;
  - по каждому вопросу «за» ставится, пока «за» не наберёт 85% участников, остальным — по очереди «против» и
    «воздержался»: 0,8 × 0,85 = 0,68 ≥ 2/3;
  - бюллетени, внесённые вручную, сохраняются и участвуют в подсчёте;
  - повторный вызов ничего не меняет.
- В обычном доме — `403 not_demo`.

### Г7. Для Димы

- **`meeting.ActiveMeeting(ctx, initiativeID) (Ref{ID, Status}, bool, error)`** — текущее собрание инициативы для
  карточки (Д4): последнее неотменённое, статус по датам. Возвращает и `completed`, чтобы карточка вела к итогу.
  Правило «нет активного собрания» для `create_meeting` — `!ok || ref.Status == "completed"`.
- **`meeting.ProtocolData(ctx, meetingID) (Protocol, error)`** — данные протокола (Д5):
  - адрес, форма, даты, номер попытки, исход;
  - председатель и секретарь с **полными** ФИО и номером квартиры;
  - общая площадь, участники, кворум;
  - по вопросам в порядке повестки: текст, правило, за / против / воздержался в м² (`*big.Rat`), принят ли.

  Всё берётся только из неизменяемого итога. До фиксации — `meeting.ErrNotFinalized` → `409 not_finalized`. Права на
  скачивание проверяет вызывающий. Проценты считаются так: для `majority_of_participants` — от `ParticipantsM2`,
  для правил «от всех» — от `TotalM2`.

### Контракт

В [API_DESCRIPTION.md](../API_DESCRIPTION.md), раздел «Собрание»:
- пометок «Каркас» больше нет;
- новый код `409 ballot_not_received`;
- в ответе `finalize` добавлены `participants_m2`, `total_m2` и `quorum_reached`;
- описаны правила предпросмотра и `fill-ballots`.

## Как проверено

```
gofmt, go vet, go test ./... -race -count=1 на PostgreSQL 18 с pool_max_conns=2 — зелёные
```

- **`TestMeetingResultIntegration`** — весь путь в демо-доме:
  - во время голосования решения, фиксация и заполнение отклоняются, отметка бюллетеня работает;
  - `finish-voting` может вызвать только администратор;
  - решения: по неполученному бюллетеню, по одному вопросу из двух, от жителя, по чужому бюллетеню — отказ;
    исправление решения работает;
  - `fill-ballots` даёт больше 2400 м², второй вызов ничего не меняет, решение, внесённое вручную, сохраняется;
  - предпросмотр: кворум есть, оба вопроса приняты;
  - две одновременные фиксации дают один итог;
  - после фиксации всё отвечает `already_finalized`, инициатива `completed`, задача в очереди, карточка с исходом;
  - `UPDATE meeting_results` падает на триггере;
  - `ProtocolData` и `ActiveMeeting`.
- **`TestMeetingInRealHouseIntegration`** — обычный дом с реестром из двух квартир:
  - голосование через 9 дней после сообщения отклоняется, через 10 — проходит;
  - собрание создаёт сотрудник УК, который не инициатор, и второй сотрудник тоже администратор;
  - демо-ускорители — `not_demo`.
- **Чистые тесты:**
  - `tally`: три доли по 1/3 дают ровно 2/3, на волосок меньше 2/3 — не принято, ровно 50% — нет кворума,
    воздержавшиеся при большинстве участников, совладельцы по 1/2 голосуют по-разному; сумма «за + против +
    воздержался» равна участникам;
  - план заполнения: 48 бюллетеней по 50 м² дают 2400 м² и 2/3, после двух ручных «против» заполняется 46, второй
    вызов пустой;
  - проверка решений: пропуск, дубль, неизвестный выбор, чужой вопрос.
- **HTTP с фейковым модулем:** тело решений и отказы на неверное, форма предпросмотра и итога, демо-ручки, коды всех
  новых ошибок.
- **Мутации:** из 11 первых 7 поймали сразу. Две выжившие указали на пробелы в тестах: фиксация без блокировки и
  ускорители в обычном доме. Для них добавлены тест одновременной фиксации и тест обычного дома, теперь они
  пойманы, как и мутация «обычный дом считается демо при проверке дат». Ещё две выжили, потому что проверка стоит
  дважды: лишнюю предварительную проверку в `Finalize` убрал, двойная проверка статуса в `ProtocolData` оставлена
  как защита.
- **Живой прогон** (приложение с `DEV_MODE`, curl):
  - отметка бюллетеня; решения и заполнение во время голосования — `voting_not_finished`;
  - `finish-voting`, решения по бюллетеню;
  - `fill-ballots`: 60 бюллетеней из 75, 2424 м²; повторно без изменений;
  - предпросмотр: кворум есть, камеры «за» 2074,5 м² из 3000 — приняты;
  - `finalize` → `held`, повторно и решения после — `already_finalized`;
  - инициатива `completed`, в очереди `meeting_created` и `meeting_finalized`, `protocol.pdf` — 501 (Д5).

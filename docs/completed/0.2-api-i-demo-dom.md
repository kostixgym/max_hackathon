# Шаг 0.2. Точка входа, демо-дом, HTTP API с проверкой `initData`

Дата: 25.09.2026. Статус: готово, ждёт ревью.

Цель шага — сервис, который запускается одной командой, сам поднимает схему, создаёт синтетический демо-дом и отдаёт
мини-приложению данные дома только после проверки, что запрос пришёл из MAX. Бот и мини-приложение — следующие шаги.

## Что сделано

```
backend/
  cmd/app/main.go                         точка входа: конфиг → БД → миграции → сид → HTTP, корректная остановка
  internal/registry/demo.go               синтетический реестр демо-дома (+ тест)
  internal/registry/seed.go               создание демо-дома в одной транзакции, идемпотентно
  internal/registry/store.go              HouseBySlug, применение версии реестра (applyVersion / setCurrentVersion)
  internal/registry/seed_test.go          интеграционный тест сида и правила «текущая версия — только применённая»
  internal/access/store.go                пользователи, привязки и защищённые каталоги собственников
  internal/platform/httpapi/auth.go       проверка initData, срок жизни запуска, режим разработки
  internal/platform/httpapi/server.go     Gin-маршруты, ответы, журнал запросов, перехват паник
  internal/platform/httpapi/profile.go    ответы привязок и замаскированных собственников
  internal/platform/httpapi/respond.go    единый формат ответов и ошибок
  internal/platform/httpapi/server_test.go  тесты API с эталонной подписью initData
  internal/platform/db/db.go              + блокировка миграций (advisory lock)
```

### Демо-дом (`registry/demo.go`, `registry/seed.go`)
- **3 подъезда × 5 этажей × 4 квартиры = 60 квартир + магазин (Н1)**, всего **ровно 3 000,00 м²**. Это пример, который везде используется в [02](../02-koncepciya-produkta.md): 10% = 300 м², кворум — больше 1 500 м², 2/3 = 2 000 м².
- Площади квартир на этаже: 34,50 / 46,00 / 48,00 / 63,50 м².
- Особые случаи из [01](../01-privyazka-k-domu.md):
  - совместная собственность по 1/2 (квартиры 3, 13, 23…);
  - по 1/3 (квартиры 7, 22, 37, 52);
  - муниципальная квартира (60);
  - магазин в собственности организации;
  - у двух третей собственников УК знает телефон, у трети — нет.
- Все имена, телефоны (`+7900…`) и лицевые счета (`DEMO-0001`…) синтетические. В БД телефоны и лицевые счета попадают только как HMAC.
- Сид создаёт версию реестра в статусе `preview`, заполняет помещения и собственников и **применяет** версию через `applyVersion`. Всё в одной транзакции.
- Идемпотентность: если демо-дом уже есть, сид ничего не делает и возвращает его ссылку. Перезапуск не плодит дома.

### Версии реестра (`registry/store.go`)
- `applyVersion` переводит версию из `preview` в `applied` и делает её текущей. Это **единственное место**, где меняется `houses.current_registry_version`.
- `setCurrentVersion` отказывает, если версия не применена (`ErrVersionNotApplied`). Вместе с составным ключом из 0.1 это даёт: текущая версия всегда существует (гарантирует БД) и всегда применена (гарантирует код, есть тест).

### API (`platform/httpapi`)

| Метод | Доступ | Что отдаёт |
|---|---|---|
| `GET /api/v1/healthz` | публично | `{"status":"ok"}` |
| `GET /api/v1/readyz` | публично | `200`, если PostgreSQL доступен; иначе `503` |
| `GET /api/v1/me` | после проверки | пользователь, `dev_mode`, дом по `start_param` и все его привязки с ролью, помещением, долей и весом |
| `GET /api/v1/houses/{slug}` | после проверки | сводка дома или `404 house_not_found` |
| `GET /api/v1/premises/{premiseID}/owners` | члену помещения или сотруднику УК | собственники помещения с замаскированным ФИО |
| `GET /api/v1/houses/{houseID}/meeting-officer-candidates` | подтверждённому собственнику или сотруднику УК | кандидаты в председатели и секретари с замаскированным ФИО |

**Сводка дома** — только то, что публично и так: адрес, регион, демо-флаг, число помещений, версия реестра, общая площадь и пороги (10%, кворум, 2/3), посчитанные модулем `rules`. Персональных данных в ней нет.

**Формат ошибок** один на всё API: `{"error": {"code": "…", "message": "…"}}`. `code` — для кода, `message` — готовый текст для пользователя.

### Проверка запроса (`auth.go`)
1. Заголовок `X-Max-Init-Data` — это `window.WebApp.initData` как есть. Подпись проверяется функцией `ValidateInitData` официального клиента MAX (HMAC с токеном бота).
2. Срок жизни запуска `auth_date` ограничен `INITDATA_MAX_AGE` (24 часа), допускается расхождение часов до 5 минут в будущее.
3. Пользователь создаётся или находится по `max_user_id` (`access.UpsertUser`), в контекст запроса кладётся `Identity`.
4. **Режим разработки** (`DEV_MODE=true`): запрос без `initData` можно подписать заголовком `X-Dev-User-Id` (и `X-Dev-Start-Param` вместо `start_param`). **Без `DEV_MODE` эти заголовки игнорируются.** При старте в этом режиме сервис пишет предупреждение в журнал.

## Решения и почему

| Решение | Почему |
|---|---|
| **Gin находится только во входящем HTTP-адаптере** | Группировка `/api/v1`, middleware и параметры пути удобнее при росте API; доменные модули и репозитории не зависят от фреймворка, а `NewHandler` по-прежнему возвращает стандартный `http.Handler` |
| **Проверка `initData` — функцией официального клиента**, а не своя реализация | Алгоритм подписи задаёт MAX, клиент поддерживает сам MAX. В тестах собственный эталонный подписчик по документации даёт ту же подпись, так что расхождений нет |
| **Причина отказа пишется в журнал, а наружу уходит общий ответ** | Подробная причина («не сошёлся хеш») помогает атакующему больше, чем пользователю |
| **`start_param` читается только из подписанного `initData`** | Ссылку дома нельзя подменить параметром запроса. Но и прав она не даёт (решение 57): по ней видна только публичная сводка |
| **Пороги и площади в API — строки с точкой (`"3000.00"`)** | Точные значения идут текстом без потерь float, форматирование с запятой — забота интерфейса |
| **Демо-дом ровно на 3 000 м²** | Цифры на демо совпадают с документами и презентацией: 300 / 1 500 / 2 000 м² видны сразу |
| **`invite_slug` демо-дома:** из `DEMO_INVITE_SLUG` или случайный, печатается в журнал | Для README и слайда жюри нужна постоянная ссылка, её задаём в `.env`. Если не задана, генерируется криптослучайная. Ссылка публичная по замыслу, печатать её безопасно |
| **Блокировка миграций в PostgreSQL** (goose session locker) | Два экземпляра, стартующие одновременно, или два пакета тестов параллельно применяют миграции по очереди. Нашёл при прогоне тестов: оба интеграционных теста мигрируют одну БД |
| **Заголовки запросов не пишутся в журнал** | В `initData` имя пользователя, это персональные данные |
| **Таймауты HTTP-сервера и корректная остановка по SIGTERM** | `docker compose stop` не обрывает запросы на середине |
| **Журнал — JSON (`slog`)** | Читается и человеком, и сборщиком логов |

## Как проверено

```
cd backend
go vet ./...        # без замечаний
go test ./...       # rules, security, registry, httpapi — ok
# с PostgreSQL 18 в Docker (см. 0.1):
TEST_DATABASE_URL=... go test ./... -count=1        # + db и registry (сид) — ok
```

Тесты API (`server_test.go`):
- правильно подписанный `initData` → 200, пользователь создан, дом по `start_param` с порогами 3000 / 300 / 1500 / 2000;
- отклоняется (401): чужой токен, устаревший на 25 часов, «из будущего», подменённый id пользователя, мусор;
- заголовок разработчика без `DEV_MODE` → 401, с `DEV_MODE` → 200;
- без учётных данных → 401; неизвестный дом → 404; `/api/v1/healthz` публичный;
- `/me` возвращает роль и вес привязки; каталоги собственников проверяют доступ и не отдают полное ФИО.

Интеграционный тест сида (`seed_test.go`):
- 61 помещение, версия 1, общая площадь 300 000 сотых м²;
- **сумма весов всех собственников ровно равна общей площади** (доли 1/2 и 1/3 ничего не теряют);
- повторный сид возвращает тот же дом;
- версия в статусе `preview` не может стать текущей.

**Живой прогон:** приложение против PostgreSQL 18 в Docker в режиме разработки:
- `/api/v1/healthz` → 200;
- `/api/v1/me` без авторизации → 401 «Откройте приложение из MAX»;
- с `X-Dev-User-Id` и ссылкой демо-дома → пользователь (UUIDv7) и сводка дома с порогами;
- неизвестный дом → 404;
- после перезапуска в БД по-прежнему один дом с той же ссылкой.

## Что не сделано в этом шаге

- **Проверка на настоящем `initData` из MAX** — шаг 0.6, нужен токен. Официальный клиент сначала декодирует строку целиком, а потом разбирает параметры. Для обычных данных это верно, но имя с символами `+` или `%` теоретически может не пройти проверку. Проверим на реальных аккаунтах.
- **Согласие на обработку персональных данных** (`users.consent_at`) — экран согласия появится вместе с подтверждением собственника (этап 1).
- **Удалённые пользователи** (`deleted_at`) пока не обрабатываются — появятся вместе с удалением аккаунта.
- **Создание и подтверждение привязки** остаётся этапом 1; уже существующие привязки `/api/v1/me` отдаёт.
- Бот — 0.3, мини-приложение — 0.4, Docker и README — 0.5.

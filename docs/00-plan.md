## Context

Хакатон MAX, трек «Умный город»: чат-бот + мини-приложение в MAX. Репозиторий пустой.

Идея команды: житель хочет поставить камеру в подъезде, а сейчас для этого нужно ходить по квартирам и собирать подписи.
Хотим, чтобы это делалось онлайн через MAX. Следующие шаги: сбор денег (идея 2) и заявки в УК с фото (идея 3).
Основной фокус на идее 1, но архитектура должна позволять добавить остальные.

## 1. Итоги исследования

### 1.1. Правовая рамка
- Камера в подъезде ставится на общее имущество дома, поэтому нужно **общее собрание собственников (ОСС) всего дома**.
  Голосуют **собственники**, голос считается **по площади**.
- **Кворум: больше 50% всех голосов** (ст. 45). **Для видеонаблюдения нужно 2/3 от всех голосов дома** (позиция ВС РФ,
  [Гарант](https://www.garant.ru/news/1430225/)). Часть судов считает, что хватает простого большинства, мы закладываем 2/3.
- **Ст. 45 ч. 6: собственники, у которых не меньше 10% голосов, вправе письменно или через ГИС ЖКХ потребовать от УК
  провести ОСС, и УК обязана сделать это за 45 дней.** ([ст. 45](https://www.consultant.ru/document/cons_doc_LAW_51057/0007bd8e825a6eadd1de1cccb256d04cb5d980c3/))
- Ст. 45 ч. 3.1: УК выдаёт реестр собственников инициатору за 5 дней. Ч. 5: обязательные реквизиты сообщения о собрании, срок уведомления — 10 дней.
- **С 01.03.2025 электронное ОСС проводится только в ГИС ЖКХ / Госуслуги.Дом или в региональной системе**, частные платформы запрещены
  ([РосКвартал](https://roskvartal.ru/news/oss-i-sobstvenniki/iz-zhk-rf-ischeznet-norma-o-provedenii-onlayn-oss-v-inyh-infosistemah)).
  В ОСС через ГИС ЖКХ можно сдать и бумажное решение администратору не позднее чем за 48 часов до конца голосования, после чего администратор вносит его в систему вручную.
- С 01.09.2025 в бумажном бюллетене обязателен СНИЛС. Протокол размещается в ГИС ЖКХ в течение 10 дней.
- Голосования в домовых чатах MAX юридической силы не имеют. ЕСИА и Госключ доступны только юрлицам через СМЭВ или API ЕПГУ, на хакатоне их не подключить.

### 1.2. Вывод
Юридическая сила решения складывается из двух частей:
1. **Правильная процедура**: повестка, уведомление, кворум, нужное большинство, протокол. **Это полностью наша зона.**
2. **Подтверждённый голос собственника**: через Госуслуги.Дом или подпись на бумаге. **Эту часть мы передаём законным каналам.**

### 1.3. Реальная боль
- Администратор ОСС в ГИС ЖКХ вручную вносит каждый бумажный голос, это «десятки часов» ([Т—Ж](https://t-j.ru/dom-gosuslugi-ru/)).
- Инициатор не знает правил (2/3 по площади, сроки, реквизиты), из-за процедурных ошибок решения признают недействительными.
- Собрать 2/3 всех голосов трудно: пожилые собственники не пользуются Госуслугами, приходится обходить квартиры вслепую.

## 2.0. Онбординг: дом → квартира → площадь

**Принцип.** Площадь и доля — свойства помещения в **реестре собственников**, который УК обязана вести (ст. 45 ч. 3.1).
Пользователь их не доказывает, мы привязываем его к записи в реестре. Кворум и 2/3 считаются от площади **всех**
помещений реестра, а не только зарегистрированных в боте.

**УК при подключении дома:** адрес, загрузка реестра (CSV: помещение, тип жилое/нежилое, площадь, собственники, доли,
лицевой счёт, телефоны по возможности), публикация ссылки на бота в домовом чате MAX, подтверждение спорных заявок.
Сверка: сумма площадей реестра против общей площади из паспорта дома (ГИС ЖКХ / Реформа ЖКХ).
Запасной вариант, если УК не участвует: инициатор загружает реестр, полученный по запросу (ст. 45 ч. 3.1).

**Выбор дома:** по ссылке `https://max.ru/<bot>?startapp=house_<id>`. Её размещают в домовом чате MAX, QR-кодом на подъезде
и в квитанции. Поиск по адресу оставляем запасным вариантом.
Гипотеза, которую нужно проверить: передаёт ли MAX `chat.id` в `initData` при запуске из группового чата. Если да, запуск из официального домового чата
(вход в него идёт через Госуслуги.Дом) подтверждает дом без дополнительных шагов.

**Уровни доверия:**
| Уровень | Как получить | Права |
|---|---|---|
| Гость | выбрал дом и квартиру сам | видит инициативу и кнопку «Подтвердить квартиру», **не голосует** |
| Житель | лицевой счёт + сумма начисления из последней квитанции (сверка с данными УК) | заявки в УК (идея 3), вопросы по инициативе, «Переслать собственнику» (`shareMaxContent`); **не голосует** |
| Собственник | телефон из `requestContact` совпал с реестром **или** житель выбрал себя из списка собственников квартиры и УК подтвердила | **единственный, кто голосует в предсборе**; голос считается в м² |
| (будущее) Госуслуги | ЕСИА через партнёрство с УК или ГИС ЖКХ | — |

**Правило: голосуют только подтверждённые собственники.** Кнопки голосования видит и получает в рассылке только собственник.
Пока подтверждение ждёт ответа УК, голосовать нельзя. Как только УК подтвердит, бот сразу присылает открытые инициативы с кнопками.

Почему этого достаточно: предсбор юридической силы не имеет, а личность при законном голосовании проверяют Госуслуги.Дом или
бумажный бюллетень с подписью и СНИЛС. Наша проверка защищает прогноз от накруток и закрывает данные дома от посторонних.

**Площадь в интерфейсе:** «Кв. 45 · 52,3 м² · доля 1/2 → ваш голос 26,15 м²». Кнопка «Данные неверны» создаёт обращение в УК.
Особые случаи: несколько собственников одной квартиры (каждый регистрируется сам), несколько помещений у одного пользователя,
нежилые помещения (тоже голосуют), муниципальные квартиры (собственник — муниципалитет, наниматели не голосуют,
но площадь входит в общий итог).

**ПДн:** УК — оператор, мы — обработчик по поручению (152-ФЗ ст. 6 ч. 3). Согласие при регистрации.
Телефоны и лицевые счета храним в виде хешей. В MVP только синтетические данные.

**Для проверки жюри:** в README и на первом слайде даём тестовые пары «лицевой счёт + сумма» и тестовый аккаунт УК для подтверждения
(или демо-режим с автоподтверждением). Телефоны жюри в реестре не найдутся, поэтому без этого пути основной сценарий не пройти.

**Модель:** `premise` (номер, тип, площадь, лицевой счёт), `owner_record` (premise, ФИО, доля, phone_hash),
`membership` (user, premise, role: resident | owner, method: phone | account | uk_manual, status: pending | verified | rejected).

## 2. Сценарий «Камера в подъезде» по шагам
Пример: дом на 60 квартир, 3 000 м². Порог 10% = 300 м², кворум больше 1 500 м², 2/3 = 2 000 м² «за».

1. **Проверка идеи** (мини-приложение). Шаблон «Видеонаблюдение»: где ставим, сколько камер, ориентир по стоимости,
   способ оплаты, кто имеет доступ к записям. Продукт формулирует вопросы повестки и показывает, **какое большинство нужно и сколько это в м² и квартирах**.
2. **Предсбор поддержки** (опрос, **без юрсилы**, так и помечен). Бот рассылает **подтверждённым собственникам** сообщение с кнопками
   «Поддерживаю / Против / Есть вопрос». Жители-несобственники получают информационное сообщение без кнопок голосования, с кнопкой «Переслать собственнику». Вопросы и ответы копятся в FAQ инициативы. Заодно собираем, как человек будет голосовать
   (Госуслуги / бумага) и готов ли помочь собирать бюллетени в своём подъезде. Дашборд показывает поддержку в м² и карту квартир по подъездам.
3. **Развилка: кто проводит ОСС**
   - **A. Через УК (основной путь).** Набрали 10% поддержки → продукт формирует **требование в УК о проведении ОСС (ст. 45 ч. 6)**
     для подписи этими ~6 собственниками (бумага или коллективная заявка в Госуслуги.Дом). УК обязана провести ОСС за 45 дней.
     Бот отслеживает этот срок и держит жителей в курсе.
   - **B. Инициатор сам.** Продукт генерирует запрос реестра в УК (срок 5 дней), сообщение о собрании, персональные бюллетени
     (PDF с QR; поле СНИЛС пустое, заполняется от руки) и план сроков. Бот напоминает о каждом шаге.
4. **Официальное голосование** (юридически значимое): онлайн в Госуслуги.Дом (кнопка ведёт туда) или бумажный бюллетень.
   Трекер по квартирам: не голосовал / онлайн / бумага получена. Прогресс к кворуму и 2/3 в м².
   Адресные напоминания только не проголосовавшим. Активист подъезда получает **список квартир для обхода**
   и сканирует QR на собранных бюллетенях (`openCodeReader`).
5. **Подсчёт и протокол**. Итоги бумажных бюллетеней вносит счётная комиссия или инициатор, онлайн-итоги берутся из ГИС ЖКХ
   (в MVP модельно). Продукт автоматически считает кворум и большинство по каждому вопросу, готовит черновик протокола
   и выгрузку для внесения бумажных голосов в ГИС ЖКХ, напоминает о сроке размещения (10 дней).
6. **Исполнение (идея 3) и деньги (идея 2)**. Решение принято → инициатива уходит в УК: исполнитель, срок, статусы жителям.
   Если нужна оплата, это строка в квитанции УК по решению ОСС. В продукте это информирование, без приёма платежей.

**Идея 3** (заявка с фото в УК) — тот же движок инициатив, только без стадии ОСС. Совпадает с ПП № 40 (обращения в MAX с 01.09.2026).

## 3. MVP (MoSCoW)

**Must**
- Бот: привязка к дому и квартире (реестр — **модельные данные**), `requestContact` для сверки с реестром, рассылка предсбора с inline-кнопками,
  напоминания, статус инициативы.
- Мини-приложение:
  - шаблон «Видеонаблюдение» + калькулятор порогов (10% / кворум / 2/3);
  - дашборд предсбора;
  - развилка A/B с генерацией PDF: требование в УК, запрос реестра, сообщение о собрании, бюллетени с QR;
  - трекер голосования по квартирам;
  - подсчёт итогов и черновик протокола.
- В интерфейсе везде видно, что перед нами: **факт, расчёт, опрос без юрсилы или модельные данные**.

**Should**: QR-скан бюллетеней (кандидат на бонус MAX), список обхода для активиста, отправка в домовой чат (`shareMaxContent`),
кабинет УК (входящие требования, срок 45 дней).

**Could**: заявка в УК с фото (идея 3) как стадия «Исполнение».

**Won't**: собственная юридически значимая подпись, реальные ЕСИА / Госключ / ГИС ЖКХ, приём платежей, хранение СНИЛС и паспортных данных.

## 4. Технологии
Архитектуру опишем позже, пока фиксируем только стек.

| Слой | Технология |
|---|---|
| **Бэкенд** | **Go** |
| **База данных** | **PostgreSQL** |
| Мини-приложение | React + TypeScript + Vite, [@maxhub/max-ui](https://github.com/max-messenger/max-ui), MAX Bridge |
| Запуск | Docker Compose |

Библиотеки Go, только открытые, со свободной лицензией. vmkteam не используем, из него берём только ревью кода.

| Задача | Библиотека |
|---|---|
| MAX Bot API | официальный клиент [max-bot-api-client-go](https://github.com/max-messenger/max-bot-api-client-go) |
| HTTP API для мини-приложения | стандартный `net/http` |
| PostgreSQL | `pgx/v5` |
| Миграции | `goose` |
| Логи | стандартный `log/slog` |
| PDF | `go-pdf/fpdf` или `maroto` + TTF-шрифт с кириллицей |
| QR-коды | `skip2/go-qrcode` |
| Тесты | стандартный `testing` |

Масштабирование: ядро неизменно (цикл инициативы, калькулятор, трекер), меняются шаблоны (домофон, шлагбаум, ремонт, смена УК),
региональные системы (например, «Электронный дом» mos.ru) и интеграция УК с ГИС ЖКХ. Канал привлечения — УК, которые с 01.09.2026 работают в MAX.

## 5. Метрики эффекта (гипотезы)
Доля инициатив, дошедших до ОСС. Доля ОСС, набравших кворум. Число квартир, которые пришлось обойти (60 → только не проголосовавшие).
Время от идеи до решения. Время на внесение бумажных голосов.

## 6. Открытые вопросы
Дедлайн онлайн-этапа, размер команды. Основной путь A или B для демо.

## 7. Проверка (после реализации)
`docker compose up --build` (не дольше 5 минут). В MAX (мобильный и веб) пройти шаги 1→5. Невалидный `initData` возвращает 401. Повторный прогон стабилен.

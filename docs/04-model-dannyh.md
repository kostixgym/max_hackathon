# Модель данных (модульный монолит)

> Статус: согласовано командой 24.09.2026. Здесь описаны сущности, связи, стадии и решения, **без** типов колонок и индексов:
> это следующий шаг (схема БД и миграции). Продуктовая логика — в [02-koncepciya-produkta.md](02-koncepciya-produkta.md),
> привязка к дому — в [01-privyazka-k-domu.md](01-privyazka-k-domu.md), архитектура — в `architecture.drawio`.

## Главные принципы

1. **Голос принадлежит собственнику, а не квартире.** Вес голоса = площадь помещения × доля собственника (по ЖК).
2. **Реестр версионируется, инициатива фиксирует версию.** Если УК перезальёт реестр посреди опроса или голосования, веса не поплывут.
3. **Опрос и официальное собрание — разные вещи и разные сущности.** Опрос юридической силы не имеет, собрание — имеет.
   Смешивать их в одной таблице нельзя.
4. **Инициатива — это жизненный цикл идеи, собрание — формальная процедура.** У одной инициативы может быть несколько собраний
   (повторное при отсутствии кворума).
5. **Камеры — только пример.** Модель поддерживает любые вопросы по дому через каталог типов решений и шаблоны.
6. **Персональные данные — по минимуму.** По квартирам видно только «голосовал / нет», как голосовали — только суммами.

## Сущности

### Дома и реестр

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **Organization** | управляющая организация | `type` (УК / ТСЖ / ЖСК; сценарии MVP только под УК), название, ИНН, контакты |
| **House** | дом | `org_id` (необязательный), адрес, код ФИАС, регион, `timezone`, площадь по паспорту дома, `registry_version` (текущая), `invite_slug` (ссылка `startapp=house_…`), `is_demo` |
| **HouseChat** | связь дома с домовым чатом MAX, куда бот публикует анонсы | дом, id чата MAX, когда добавлен |
| **RegistryUpload** | факт загрузки реестра | дом, версия, кто и когда загрузил, сверка суммы площадей с паспортом |
| **Premise** | помещение в конкретной версии реестра | дом, `registry_version`, номер, вид (жилое / нежилое / машиноместо), площадь, подъезд, этаж, `account_hash` (хеш лицевого счёта) |
| **OwnerRecord** | запись о собственнике в конкретной версии реестра | помещение, `registry_version`, ФИО, доля (`share_num` / `share_den`), вид собственника (гражданин / организация / муниципалитет), `phone_hash` |

### Пользователи и доступ

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **User** | пользователь MAX | `max_user_id`, согласие на обработку ПДн, удалён ли. Имя и фото из MAX не храним |
| **Membership** | привязка пользователя к помещению | пользователь, помещение, роль (гость / житель / собственник), `owner_record_id` (только у собственника), способ подтверждения (телефон / квитанция / УК / демо), статус (ожидает / подтверждён / отклонён / отозван), кто и когда подтвердил |
| **OrgMember** | сотрудник УК | пользователь, организация, роль (администратор / оператор) |

### Правила и шаблоны (в БД, правит только платформа)

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **DecisionType** | тип решения по ЖК со своим правилом большинства | код, название, правило большинства (например, 2/3 от всех / большинство участников / больше 50% от всех), ссылка на норму |
| **Template** | готовый сценарий инициативы (камеры, домофон, ремонт…) | код, название, версия, `params_schema` (описание полей формы) |
| **TemplateItem** | вопрос повестки в шаблоне | шаблон, порядок, текст, тип решения |

### Инициативы

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **Initiative** | жизненный цикл идеи | дом, `type` (сейчас «собрание»; потом «сбор средств», «заявка»), шаблон и его версия, название, описание, `params` (JSONB, значения по схеме шаблона), `stage`, `path` (A / B), `registry_version`, срок опроса, итог, кто отменил и причина |
| **InitiativeParticipant** | люди с ролями в инициативе | инициатива, пользователь, роль (инициатор / автор идеи / активист), подъезд (для активиста) |
| **AgendaItem** | вопрос повестки конкретной инициативы | инициатива, порядок, текст, тип решения |
| **InitiativeQuestion** | вопрос соседа и ответ | инициатива, автор, текст, ответ, опубликован ли в FAQ, когда отвечен |
| **InitiativeMute** | отписка от напоминаний по инициативе | пользователь, инициатива |
| **Deadline** | контрольный срок | инициатива или собрание, вид (реестр 5 дней / УК 45 дней / уведомление 10 дней / конец опроса / конец голосования / протокол 10 дней), `due_at`, статус |
| **StageEvent** | журнал смены стадий | инициатива, из какой, в какую, кто, когда, причина |

### Опрос поддержки (без юридической силы)

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **PollVote** | голос собственника в опросе | инициатива, `owner_record_id`, пользователь, выбор (за / против), как удобнее голосовать официально (Госуслуги / бумага), «готов помочь», время. Уникален на пару «инициатива + собственник» |
| **PollTally** | готовый прогресс опроса | инициатива, м² «за», м² «против», количество голосов, версия (для ETag) |

### Требование в УК (путь A)

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **Demand** | требование собственников провести собрание (ст. 45 ч. 6 ЖК) | инициатива, канал (бумага / Госуслуги.Дом), когда передано, набранная площадь, срок УК (45 дней) |
| **DemandSignature** | кто подписал требование | требование, `owner_record_id`, кто и когда отметил |

### Официальное собрание

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **Meeting** | ОСС | инициатива, номер попытки, форма (электронное в ГИС ЖКХ / заочное на бумаге), администратор (УК или инициатор), даты уведомления, начала и конца голосования, `external_ref` (ссылка на собрание в ГИС ЖКХ), `status` |
| **MeetingRole** | председатель, секретарь, счётная комиссия | собрание, `owner_record_id`, роль |
| **Ballot** | учёт голоса собственника на собрании | собрание, `owner_record_id`, канал (онлайн / бумага), статус (не голосовал / онлайн со слов / бумага получена / учтён / недействителен), `qr_token`, кто и когда принял, причина недействительности |
| **BallotDecision** | решение из бумажного бюллетеня по вопросу | бюллетень, вопрос повестки, решение (за / против / воздержался) |
| **GisResultEntry** | итоги онлайн-голосования из ГИС ЖКХ, внесённые вручную | собрание, вопрос повестки, м² за / против / воздержался, кто внёс |
| **MeetingResult** | итог по вопросу | собрание, вопрос, площадь участников (кворум), м² за / против / воздержался, принят ли, когда зафиксирован |

### Документы и служебное

| Сущность | Назначение | Ключевые поля |
|---|---|---|
| **Document** | итоговый документ (протокол, требование, сообщение о собрании) | инициатива / собрание, вид, хеш содержимого, где лежит файл, когда создан. Неизменяемый |
| **OutgoingMessage** | отправленное ботом сообщение | получатель (пользователь или чат), инициатива, вид, `max_message_id` (чтобы отредактировать сообщение, например на «Голос учтён»), когда отправлено |
| **AuditLog** | журнал действий | кто, что сделал, над чем, когда, данные изменения |

## Стадии

Стадии хранятся **в два уровня**: инициатива отвечает за путь идеи, собрание — за формальную процедуру.

### `Initiative.stage`

```
черновик ──► опрос ──┬─ путь A (≥10% «за») ──► требование в УК ──► собрание ──► итог
   │                 └─ путь B ─────────────────────────────────►  собрание ──► итог
   │                                         (УК просрочила 45 дней → путь B)
   └─ инициатива УК (опрос по желанию) ────────────────────────►  собрание ──► итог

итог «нет кворума» ──► повторное собрание (новый Meeting в той же инициативе)
любая стадия ──► отменена (кто отменил + обязательная причина, видна жителям)
```

- **Черновик → опрос:** запускает подтверждённый собственник. Черновик жителя-несобственника сначала должен принять собственник, он и становится инициатором.
- **Опрос → путь A или B:** выбирает инициатор по итогам опроса. Путь A доступен при ≥10% площади «за» и помечен как рекомендуемый.
- **Требование → собрание:** сотрудник УК создаёт `Meeting` в своём кабинете и становится администратором.
- **Просрочка УК (45 дней):** инициатор получает уведомление и два действия: провести собрание самому (путь B) и скачать готовую жалобу в жилищную инспекцию. Жители видят факт просрочки.
- **Итог:** «принято», «не принято», «нет кворума».

### `Meeting.status`

```
подготовка ──► уведомление (10 дней) ──► голосование ──► подсчёт ──► завершено
```

## Кто что может

| Роль | Что может |
|---|---|
| **Гость** | видит название инициативы и приглашение подтвердить квартиру |
| **Житель** (не собственник) | видит инициативы и прогресс в м², задаёт вопросы, создаёт черновик инициативы, пересылает инициативу собственнику. **Не голосует** |
| **Собственник** | всё, что житель, плюс голосует в опросе (менять голос можно до перехода к собранию), создаёт инициативу и запускает опрос |
| **Инициатор** | ведёт свою инициативу: срок опроса, выбор пути A/B, отметка подписей требования, назначение активистов, ответы на вопросы и публикация FAQ, правка (голоса опроса при этом сбрасываются), отмена. По квартирам видит только «голосовал / нет» |
| **Активист подъезда** | получает список обхода, отмечает «бюллетень получен» (скан QR) |
| **Счётная комиссия** (MeetingRole) | после окончания голосования вносит решения из бумажных бюллетеней. Промежуточного итога никто не видит |
| **Администратор собрания** (УК или инициатор) | вносит официальные итоги из ГИС ЖКХ по каждому вопросу |
| **Сотрудник УК** | подключает дом и загружает реестр, подтверждает собственников (кроме себя), создаёт собрание по требованию, создаёт свои инициативы (без пути A), отменяет инициативы с причиной. По опросам собственников видит только суммы в м² |
| **Администратор платформы** | ведёт типы решений и шаблоны, может отменить инициативу с причиной |

Один пользователь может совмещать роли, например быть и собственником, и сотрудником УК (переключатель «Жилец / УК»).

## Решения

Номера совпадают с планом в [00-plan.md](00-plan.md).

### Голоса и веса
- **1.** Голос в опросе и собрании привязан к собственнику (`OwnerRecord`), вес = площадь × доля.
- **3.** Голос в опросе можно менять до перехода к официальному собранию, потом опрос замораживается.
- **4.** Варианты опроса — «За» / «Против». Кнопка «Есть вопрос» голосом не считается.
- **20.** Инициатор видит по квартирам только «голосовал / нет», как голосовали — только суммами в м².
- **36.** Веса считаются точно: площадь — десятичное число, доля — числитель и знаменатель. Суммы без округления, до 0,01 м² округляем только при показе и в протоколе.
- **43.** УК видит по опросу собственника только суммы в м².

### Инициатива, повестка, шаблоны
- **5.** `Initiative` и `Meeting` — разные сущности, 1 : N; повторное собрание идёт в рамках той же инициативы.
- **6.** Повестка — несколько вопросов, у каждого своё большинство. В опросе один вопрос: «поддерживаете идею?».
- **7, 9.** Типы решений и шаблоны хранятся в БД с версиями, правит только платформа. В MVP заводятся сидом в миграции, админки нет.
- **12, 13.** Любые кейсы поддерживаются тремя уровнями: каталог типов решений (правило большинства) → шаблоны (наборы вопросов с типами) → свой вопрос (инициатор пишет текст и выбирает тип, большинство берётся из типа).
- **14.** В шаблоне хранится схема полей формы, в инициативе — значения в JSONB. Форма мини-приложения строится по схеме.
- **15.** Общая `Initiative` с полем `type` держит жизненный цикл, дом, участников и уведомления, а специфика вынесена в отдельные таблицы: сейчас `Meeting`, потом `Fundraising`, `IssueReport`.
- **16.** Финал в MVP: «принято», «не принято», «нет кворума» (можно повторить собрание), «отменена». Исполнение решения — позже.
- **11, 49.** Участники инициативы — таблица `InitiativeParticipant` с ролями (инициатор, автор идеи, активист + подъезд). В MVP инициатор один, модель готова к соинициаторам.
- **27.** Активных инициатив в доме может быть сколько угодно. При создании по тому же шаблону система предлагает присоединиться к существующей.
- **33, 37.** Инициативу можно править и после старта опроса, но голоса опроса удаляются, а собственникам уходит повторная рассылка. Ревизии не храним, правка фиксируется в `AuditLog`.

### Кто создаёт и отменяет
- **8.** Создать инициативу могут подтверждённый собственник, сотрудник УК (ст. 45 ч. 7 ЖК) и житель-несобственник (только черновик).
- **10.** Инициатива УК идёт без пути A: УК сама созывает собрание, опрос по желанию.
- **34, 38, 39.** Отменить инициативу на любой стадии, включая голосование, могут инициатор, сотрудник УК и администратор платформы. Причина обязательна и видна всем подтверждённым жителям, инициатор получает уведомление.
- **41.** Один пользователь может быть и сотрудником УК, и собственником. Свою заявку на подтверждение сотрудник подтвердить не может.

### Опрос
- **17.** Опрос обязателен для инициативы собственника (он нужен для 10% на путь A), для инициативы УК — по желанию.
- **18.** Срок опроса задаёт инициатор (по умолчанию 7 дней). По окончании бот присылает итог и предлагает следующий шаг, перейти дальше можно досрочно.
- **19.** Инициативу и прогресс видят все подтверждённые жители, гость — только название и приглашение подтвердиться.
- **30.** Вопросы соседей видит инициатор. После ответа пара «вопрос — ответ» попадает в публичный FAQ без имени автора, но инициатор может ответ не публиковать.

### Путь A / B и собрание
- **45.** Путь A или B выбирает инициатор после опроса. Путь A доступен при ≥10% площади и помечен как рекомендуемый.
- **46.** Путь A: требование попадает в кабинет УК, сотрудник создаёт `Meeting` и становится администратором.
- **47.** Если УК просрочила 45 дней, инициатору предлагается путь B и готовая жалоба в жилищную инспекцию, жители видят просрочку.
- **48.** Стадии в два уровня: `Initiative.stage` и `Meeting.status` (см. раздел «Стадии»).
- **23.** Формы собрания: электронное в ГИС ЖКХ (в MVP модельно; бумажные решения сдаются администратору) и заочное на бумаге. Очное и очно-заочное не поддерживаем.
- **24.** Онлайн-голоса: во время голосования собственник сам отмечает «проголосовал онлайн» (для трекера), после окончания администратор вручную вносит официальные итоги из ГИС ЖКХ (`GisResultEntry`). Импорт через интеграцию — в будущем.
- **25.** `MeetingRole`: председатель, секретарь, счётная комиссия. Попадают в протокол и получают право вносить бюллетени.
- **26.** Во время голосования активист отмечает только «бюллетень получен». Решения вносит счётная комиссия после окончания.
- **32.** Собственник отмечает в опросе «готов помочь», инициатор назначает его активистом подъезда.

### Реестр
- **2.** Инициатива фиксирует версию реестра (`registry_version`), все веса считаются по ней. Новая версия применяется к следующему собранию.
- **21.** Новая версия реестра — новые строки `Premise` и `OwnerRecord`, старые не меняются.
- **22.** При новом реестре привязки переносятся автоматически, если собственник тот же (помещение + ФИО + хеш телефона). Если собственник исчез, роль снимается, а спорные случаи уходят на проверку УК.
- **31.** `Organization.type` (УК / ТСЖ / ЖСК) есть в модели, но сценарии MVP только под УК.
- **42.** Дом без УК в MVP не поддерживаем, но `House.org_id` необязательный.

### Уведомления и чат
- **29.** Тихие часы с 22:00 до 9:00 по часовому поясу дома и отписка от напоминаний по инициативе. Важные события (старт собрания, итог) приходят всегда.
- **44.** Голосование и напоминания — только в личных сообщениях. Если УК добавила бота в домовой чат (`HouseChat`), бот публикует там анонсы со ссылкой.

### Данные и документы
- **28.** При отзыве согласия или удалении аккаунта удаляем аккаунт, привязки и голоса опроса (прогресс пересчитывается). Учёт официальных бюллетеней и итоги собрания остаются: они привязаны к реестру УК, а не к аккаунту.
- **35.** Итоговые документы (протокол, требование, сообщение о собрании) храним неизменяемыми версиями с хешем. Персональные бюллетени генерируем по запросу и не храним.
- **40.** Идентификаторы — UUIDv7 везде.
- **51.** Демо-режим — флаг `House.is_demo`: в демо-доме заявки подтверждаются сразу, в интерфейсе плашка «демо-данные».

### Вне MVP
- **50.** Совет дома не моделируем, позже он станет ролью собственника.
- **52.** Деньги не моделируем: стоимость остаётся в тексте вопроса или описании.
- Также вне MVP: дома без УК, очные и очно-заочные собрания, собрания членов ТСЖ, импорт итогов из ГИС ЖКХ, интерфейс для соинициаторов.

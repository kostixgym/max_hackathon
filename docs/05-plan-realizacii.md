# План реализации

> Что и почему делаем — в [02-koncepciya-produkta.md](02-koncepciya-produkta.md) и [04-model-dannyh.md](04-model-dannyh.md).
> Здесь — **в каком порядке, кто делает и когда этап считается готовым.**
> Допущения: команда из 3 человек, дедлайн онлайн-этапа пока неизвестен. План разбит на этапы с критериями выхода;
> когда дедлайн станет известен, этапы раскладываются по датам (ориентир по времени: 10% / 35% / 40% / 15%).

## Главное правило

**Сначала сквозной сценарий в настоящем MAX, потом глубина.** По критериям допуска бот, который не запускается, даёт 0 баллов.
А «работоспособность основного сценария» — самый тяжёлый технический критерий (30%). Поэтому каждый этап заканчивается
тем, что основной сценарий проходится целиком в мобильном и веб-MAX.

## Этап 0. Платформа и контракты (~10%)

**Цель:** снять главный риск допуска и договориться о контрактах, чтобы дальше работать параллельно.

| Участник 1 (платформа, доступ) | Участник 2 (ядро) | Участник 3 (мини-приложение, продукт) |
|---|---|---|
| каркас репозитория, compose (db + app + web), Caddy с HTTPS, деплой на VPS | миграции таблиц модулей «Реестр домов» и «Доступ и роли», сид демо-дома (~60 помещений) | каркас мини-приложения с MAX UI и MAX Bridge, экран «Мой дом» на заглушках |
| бот отвечает на `/start`, кнопка открывает мини-приложение | модуль «Правила ЖК»: калькулятор порогов (10%, кворум, 2/3) + тесты | сценарий демо по экранам, список сообщений бота |
| проверка `initData` (HMAC, свежесть), режим разработки без MAX (фейковые события) | черновик каталога `DecisionType` по ст. 44/46 ЖК | скелет README по чек-листу со с. 9, `.env.example`, `.dockerignore` |

**Вместе:** контракт API мини-приложения (TypeScript-типы или OpenAPI для внутреннего использования), интерфейсы между модулями, тексты сообщений бота.

**Проверить на выданном токене** (результаты записать в 04, раздел «Открытые вопросы»):
- возвращает ли «Поделиться номером» номер телефона;
- передаётся ли `chat.id` в `initData` при запуске из группового чата;
- работает ли сканер QR в веб-версии MAX (если нет, нужен ввод номера квартиры вручную);
- лимиты MAX API на отправку сообщений.

**Готово, когда:**
- в мобильном **и** веб-MAX бот отвечает, мини-приложение открывается из бота и получает с бэкенда данные демо-дома;
- `docker compose up --build` поднимает всё с нуля за время меньше 5 минут;
- калькулятор порогов покрыт тестами.

## Этап 1. Сквозной скелет (~35%)

**Цель:** основной сценарий проходит от начала до конца, пусть без красоты и в самой простой версии каждого шага.

Сценарий этапа (путь A, демо-дом):

> ссылка дома → вход в демо-режиме (автоподтверждение собственника) → инициатива по одному шаблону → опрос кнопками в чате →
> прогресс в м² → требование в УК → сотрудник УК создаёт собрание → отметка бюллетеней по номеру квартиры →
> внесение решений → фиксация итога → черновик протокола (PDF)

| Участник 1 | Участник 2 | Участник 3 |
|---|---|---|
| вход по `invite_slug`, демо-подтверждение, роли и права на каждом запросе | инициативы и повестка из шаблона, снимок реестра | экраны: создание инициативы по шаблону, прогресс опроса |
| очередь задач и рассылка опроса, ответ «Голос учтён» через `POST /answers` | опрос (`PollVote`, вес в строке голоса, прогресс на лету), требование (`Demand`) | экраны: требование, собрание, отметка бюллетеней, итог |
| минимальный кабинет УК: список требований, создание собрания | собрание, бюллетени, решения, фиксация итога (write-once), PDF протокола | «капитан сценария»: каждый день проходит сценарий целиком в мобильном и веб-MAX |

**Готово, когда:** сценарий выше проходится целиком в настоящем MAX двумя аккаунтами (инициатор и сосед) и повторяется без сбоев.

## Этап 2. Глубина по приоритету (~40%)

Делаем сверху вниз. Если время кончается, нижние пункты переходят в «известные ограничения».

1. **Тесты на подсчёт:** веса с долями, пороги от снимка, правила большинства, отсутствие кворума. Ошибка в м² убивает доверие к продукту.
2. **Три пути подтверждения собственника** (телефон → квитанция → УК) и конфликт «один собственник — одна привязка».
3. **Состояния интерфейса:** загрузка, пустые данные, ошибки, повтор после ошибки (отдельный пункт критерия UX).
4. **Трекер голосования и напоминания:** задачи очереди, тихие часы, «со слов» vs официальные данные, предупреждение при расхождении.
5. **Внесение итогов ГИС ЖКХ** и правила отмены (включая «отменяется → отменено»).
6. **Каталог `DecisionType` и 2–3 шаблона** (например, камеры, домофон, ремонт подъезда) + свой вопрос с выбором типа.
7. **Путь B:** запрос реестра, сообщение о собрании, персональные бюллетени с QR (PDF).
8. **Сканер QR на бюллетенях** — кандидат на бонус за расширенное использование MAX.
9. **Загрузка реестра с отчётом сопоставления**, включая предупреждение «сумма долей помещения ≠ 1» (без блокировки загрузки).

**Готово, когда:** пункты 1–5 сделаны, основной сценарий стабилен при повторных прогонах, ошибки обрабатываются без перезапуска.

## Этап 3. Сдача (~15%)

- **README по чек-листу** (с. 9 методички), включая тестовые данные для жюри: пары «лицевой счёт + сумма», демо-дом, как пройти сценарий.
- **Docker:** проверка сборки на чистой машине (≤ 5 минут), `.env.example` без секретов, секретов нет в репозитории.
- **Интеграционный тест схемы БД** запускается одной командой локально и в CI (сервис `postgres:18`).
- **Известные ограничения** и **модельные данные** явно перечислены (требование методички).
- **Презентация PDF:** первый слайд — техническая информация (ссылка на бота, репозиторий и commit hash, тестовые данные, порядок проверки); дальше продуктовая часть.
- **Финальный прогон** в мобильном и веб-MAX, **заморозка кода**, фиксация commit hash.

## Что выкидываем при нехватке времени

В порядке очереди на выброс:
1. загрузка реестра с отчётом → остаётся только сид демо-дома;
2. путь B → остаётся только путь A;
3. сканер QR → отметка по номеру квартиры;
4. дополнительные шаблоны → остаётся один;
5. пути подтверждения по квитанции и через УК → остаётся телефон + демо-режим;
6. напоминания по срокам → остаётся только рассылка опроса.

**Не выкидываем никогда:** сквозной сценарий, проверку `initData` и прав, точный подсчёт, README и Docker.

## Постоянные практики

- **Ветки короткие, ревью обязательно:** участники 1 и 2 проверяют код друг друга (можно через `go-review`), участник 1 смотрит работу участника 3 со стороны контракта API.
- **`main` всегда рабочий** и автоматически выкатывается на тестовый сервер с настоящим токеном. Локально разработка идёт в режиме без MAX.
- **Каждый день прогон основного сценария** в мобильном и веб-MAX.
- **Изменения модели** сначала вносятся в [04-model-dannyh.md](04-model-dannyh.md), потом в миграции.

## После MVP: рост инфраструктуры

Заранее не делаем: каждый компонент добавляется, когда есть измеримая причина. Этапы совпадают с вкладкой 5 в `03-arhitektura.drawio`.

| Этап | Что меняется | Когда |
|---|---|---|
| 1. MVP | один процесс (app + worker), один PostgreSQL, бот через long polling | сейчас |
| 2. Пилот | app и worker — отдельные процессы из одного образа | тяжёлые рассылки или PDF начинают тормозить ответы пользователю |
| 3. Город / регион | N копий app за балансировщиком, бот через webhook, N воркеров, реплики PostgreSQL на чтение, **PgBouncer** | суммарное число соединений (копии × размер пула) подходит к `max_connections` PostgreSQL (по умолчанию 100) |
| 4. По необходимости | вынос уведомлений и интеграций в отдельные сервисы | см. вкладку 7 drawio |

### PgBouncer (этап 3)

Нужен не для скорости, а чтобы экономить соединения с PostgreSQL, когда копий приложения много.
Альтернатива — управляемый PostgreSQL в облаке со встроенным менеджером подключений (в Yandex Cloud это Odyssey).

Работает только в режиме `transaction`, и в нём не действует всё, что привязано к сессии. Условия для нашего кода:

| Что сломается | Решение |
|---|---|
| Блокировка миграций goose (`pg_advisory_lock` на уровне сессии) | миграции ходят в БД напрямую: отдельная настройка с прямым адресом БД, по умолчанию равна `DATABASE_URL` |
| Автоматические подготовленные запросы pgx | PgBouncer **1.21+** с `max_prepared_statements > 0` (код не меняется); иначе `DefaultQueryExecMode = QueryExecModeExec` в pgx |
| LISTEN/NOTIFY: мгновенный подхват задач очередью River, сброс кэша по событиям | координатору очереди — прямое соединение с БД, вставка задач и воркеры — через PgBouncer; либо режим River `PollOnly` |

Уже написанный код в остальном совместим: `pg_advisory_xact_lock` в сиде действует в пределах транзакции, все записи идут в явных транзакциях.

Источники: [River: PgBouncer](https://riverqueue.com/docs/pgbouncer), [pgx](https://pkg.go.dev/github.com/jackc/pgx/v5),
[pganalyze: prepared statements в PgBouncer 1.21](https://pganalyze.com/blog/5mins-postgres-pgbouncer-prepared-statements-transaction-mode).

## Риски

| Риск | Что делаем |
|---|---|
| Один токен — один получатель событий | локальная разработка без MAX; настоящий токен только на тестовом сервере; спросить организаторов про второй токен |
| Возможности MAX отличаются от ожидаемых (номер телефона, `chat.id`, QR в веб-версии) | проверяем в этапе 0, запасные варианты уже описаны |
| Ошибка в подсчёте | тесты на расчёты в приоритете №1 этапа 2 |
| Каталог `DecisionType` требует юридической проверки | начать в этапе 0, в MVP — минимальный набор под шаблоны |
| Не укладываемся в срок | список «что выкидываем», сквозной сценарий готов уже после этапа 1 |

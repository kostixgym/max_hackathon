# План Гоши: Г8 — результаты ГИС ЖКХ

> Статус: выполнено 27.09.2026. Реализация и проверки описаны в
> [completed/sobranie-g8.md](completed/sobranie-g8.md).

## 1. Цель и границы задачи

Оставшаяся задача Гоши — реализовать `PUT /api/v1/meetings/{id}/gis-results` и учитывать официальные агрегаты
ГИС ЖКХ в предпросмотре и при окончательной фиксации результата собрания.

После выполнения задачи итог собрания должен складываться из двух официальных источников:

1. учтённых бумажных бюллетеней (`ballots.status = counted` и `ballot_decisions`);
2. агрегированных результатов онлайн-голосования из `gis_result_entries`.

Вне задачи:

- интеграция с настоящим API ГИС ЖКХ — данные вводятся вручную;
- отметка жителем «проголосовал онлайн» — она не является официальным голосом;
- путь B и самостоятельная организация собрания;
- PDF и остальные документы.

Новая миграция не требуется. В схеме уже есть:

- `gis_result_entries` с уникальностью `(meeting_id, agenda_item_id)`;
- `meetings.online_participants_weight_num/den`;
- `meetings.participants_weight_num/den` для зафиксированного общего числа участников.

## 2. Сначала зафиксировать контракт

Запрос:

```http
PUT /api/v1/meetings/{meeting_id}/gis-results
Content-Type: application/json
```

```json
{
  "entries": [
    {
      "agenda_item_id": "0199...",
      "for_m2": "1800.00",
      "against_m2": "100.00",
      "abstain_m2": "50.00"
    }
  ],
  "online_participants_m2": "1950.00"
}
```

Успешный ответ `200 OK` возвращает сохранённые данные в том же порядке, что и вопросы повестки:

```json
{
  "entries": [
    {
      "agenda_item_id": "0199...",
      "for_m2": "1800.00",
      "against_m2": "100.00",
      "abstain_m2": "50.00"
    }
  ],
  "online_participants_m2": "1950.00"
}
```

Принять следующие правила:

- значения площади приходят строками и разбираются без `float64`;
- допустимы неотрицательные десятичные числа с точностью не больше двух знаков после точки;
- в запросе должен быть ровно один результат для каждого вопроса повестки;
- неизвестные вопросы, пропущенные вопросы и дубли запрещены;
- для каждого вопроса `for_m2 + against_m2 + abstain_m2` должно равняться `online_participants_m2`;
- онлайн-площадь не может превышать общую площадь снимка реестра;
- результаты ГИС принимаются только для собрания формы `gis_electronic`;
- данные можно внести или исправить только после окончания голосования и до финализации;
- действие доступно только администратору собрания через существующую проверку `mustRun`;
- повторный `PUT` до финализации полностью заменяет агрегаты предыдущего ввода.

Предлагаемые ошибки API:

| Условие | HTTP | Код |
|---|---:|---|
| некорректный JSON или площадь | 400 | `invalid_request` |
| неполная повестка, дубль, неверная сумма | 400 | `invalid_gis_results` |
| собрание не найдено | 404 | `meeting_not_found` |
| пользователь не администратор | 403 | `staff_only` |
| голосование ещё идёт | 409 | `voting_not_finished` |
| форма собрания не поддерживает ГИС | 409 | `gis_results_not_allowed` |
| итог уже зафиксирован | 409 | `already_finalized` |

## 3. Доменная модель

### 3.1. Добавить типы и ошибки

В `backend/internal/meeting/meeting.go` либо в новом `gis.go` добавить:

```go
type GISResultEntry struct {
    AgendaItemID string

type GISResults struct {
    Entries             []GISResultEntry

```

Также понадобятся доменные ошибки:

- `ErrInvalidGISResults`;
- `ErrGISResultsNotAllowed`.

Не использовать HTTP-коды и JSON-типы внутри пакета `meeting`.

### 3.2. Проверка и упорядочивание данных

Сделать чистую функцию, похожую на `orderDecisions`:

```go
func orderGISResults(
    agenda []initiatives.AgendaItem,
    entries []GISResultEntry,
    onlineParticipants *big.Rat,
    total *big.Rat,
) ([]GISResultEntry, error)
```

Функция должна:

1. проверить, что `onlineParticipants` задан и неотрицателен;
2. проверить неотрицательность всех трёх значений каждого вопроса;
3. отвергнуть дубли;
4. потребовать все вопросы повестки;
5. вернуть записи в порядке `agenda_items.position`;
6. проверить сумму голосов по каждому вопросу;
7. проверить, что онлайн-участники не превышают общую площадь дома.

Эту функцию покрыть unit-тестами отдельно от базы данных.

## 4. Сохранение результатов ГИС

Создать `backend/internal/meeting/gis.go` с методом сервиса:

```go
func (s *Service) RecordGISResults(
    ctx context.Context,
    meetingID string,
    byUserID string,
    input GISResults,
) (GISResults, error)
```

Порядок работы метода:

1. Загрузить собрание через `s.load`.
2. Проверить администратора через `s.mustRun`.
3. Проверить `meeting.Form == FormGISElectronic`.
4. Если собрание завершено — вернуть `ErrAlreadyFinalized`.
5. Если голосование ещё идёт — вернуть `ErrVotingNotFinished`.
6. Проверить и упорядочить данные через `orderGISResults`.
7. Открыть одну транзакцию через `TransactionManager`.
8. Заблокировать собрание через `lockMeeting(..., "FOR UPDATE")`.
9. Записать все вопросы в `gis_result_entries` через `INSERT ... ON CONFLICT DO UPDATE`.
10. При обновлении заменить площади, `entered_by_user_id` и `updated_at`.
11. Записать `online_participants_weight_num/den` в `meetings`.
12. Вернуть упорядоченные сохранённые данные.

`FOR UPDATE` нужен, чтобы два одновременных ввода ГИС или ввод одновременно с `Finalize` не дали частично смешанный
результат. Если `Finalize` успел первым, `lockMeeting` должен вернуть `ErrAlreadyFinalized`.

Для записи дробей использовать существующий `centi`/`centiAll`: значения в Go остаются точными `big.Rat`, в БД
хранятся как числитель и знаменатель сотых квадратного метра.

## 5. Чтение официальных онлайн-результатов

В `gis.go` добавить внутренний метод:

```go
func (s *Service) gisResults(
    ctx context.Context,
    q querier,
    meetingID string,
) (GISResults, error)
```

Он должен:

- прочитать `online_participants_weight_num/den` из `meetings`;
- прочитать строки `gis_result_entries`;
- преобразовать хранимые сотые м² обратно в `*big.Rat`;
- вернуть нулевую онлайн-площадь и пустой список, если результаты ГИС ещё не внесены;
- работать как с пулом, так и с транзакцией через `querier`.

## 6. Объединение ГИС и бумажных бюллетеней

Изменить подсчёт в `backend/internal/meeting/result.go`.

Текущий `tally` считает только бумажные бюллетени. После изменения он должен принимать и результаты ГИС:

```go
func tally(
    total *big.Rat,
    ballots []countedBallot,
    gis GISResults,
    agenda []initiatives.AgendaItem,
) (Result, error)
```

Алгоритм:

1. `participants_m2 = online_participants_m2 + сумма весов учтённых бумажных бюллетеней`.
2. Для каждого вопроса начать с агрегатов ГИС.
3. Добавить голоса бумажных бюллетеней.
4. Проверить, что общая площадь участников не превышает площадь снимка.
5. Рассчитать кворум через `rules.QuorumReached`.
6. Рассчитать принятие каждого вопроса через `rules.Passed`.
7. Без кворума все вопросы должны иметь `accepted = false`.

Изменить оба места вызова:

- `Preview` читает бумажные бюллетени и ГИС через пул;
- `Finalize` после блокировки собрания читает оба источника внутри одной транзакции.

Это важно: `Finalize` не должен использовать результаты, прочитанные до транзакционной блокировки.

Запись в `meeting_results`, завершение собрания, смена стадии инициативы и уведомление остаются в существующей
транзакции без изменения общей последовательности.

`ProtocolData` менять не требуется: после финализации он уже читает `meeting_results` и сохранённую общую площадь
участников.

## 8. Unit-тесты подсчёта

Расширить `backend/internal/meeting/result_test.go`.

Обязательные сценарии:

1. Пустые результаты ГИС сохраняют старое поведение бумажного подсчёта.
2. Только ГИС: участники и голоса берутся из онлайн-агрегатов.
3. ГИС плюс бумага: площади и голоса суммируются.
4. Ровно 50% общей площади — кворума нет.
5. Больше 50% — кворум есть.
6. Ровно 2/3 всех голосов «за» — вопрос принят.
7. Чуть меньше 2/3 — не принят.
8. Воздержавшиеся корректно влияют на `majority_of_participants`.
9. Сумма онлайн-участников и бумаги больше общей площади — ошибка.
10. Доли бумажных собственников `1/2` и `1/3` остаются точными при сложении с ГИС.

Отдельно добавить unit-тесты `orderGISResults`:

- правильная сортировка по повестке;
- пропущенный вопрос;
- неизвестный вопрос;
- один вопрос дважды;
- отрицательное значение;
- сумма по вопросу не совпадает с участниками;
- онлайн-площадь больше площади дома.

## 9. Интеграционный тест PostgreSQL

Расширить `TestMeetingResultIntegration` либо добавить отдельный `TestGISResultsIntegration` в
`backend/internal/meeting/meeting_integration_test.go`.

Полный сценарий:

1. Создать собрание формы `gis_electronic`.
2. Попытаться внести ГИС до окончания голосования — получить `ErrVotingNotFinished`.
3. Завершить голосование демо-ускорителем.
4. Попытаться внести данные обычным жителем — получить `ErrStaffOnly`.
5. Внести корректные результаты администратором.
6. Проверить строки `gis_result_entries` и `online_participants_weight_num/den` напрямую в БД.
7. Повторить `PUT` с исправленными значениями и убедиться, что строки обновились, а не продублировались.
8. Добавить один или несколько учтённых бумажных бюллетеней.
9. Получить `Preview` и проверить сумму ГИС и бумаги.
10. Вызвать `Finalize`.
11. Проверить `meeting_results`, общую площадь участников, кворум и решения.
12. Попытаться изменить ГИС после фиксации — получить `ErrAlreadyFinalized`.

Дополнительно проверить собрание `paper_absentee`: ввод ГИС должен вернуть `ErrGISResultsNotAllowed`.

## 12. Критерии готовности

Г8 считается завершённой, когда одновременно выполнены все условия:

- маршрут `PUT /api/v1/meetings/{id}/gis-results` зарегистрирован и защищён авторизацией;
- точные агрегаты по всем вопросам сохраняются одной транзакцией;
- повторный ввод до финализации корректирует данные;
- предпросмотр объединяет ГИС и бумажные бюллетени;
- финализация фиксирует объединённый результат и общую площадь участников;
- после финализации данные ГИС изменить нельзя;
- права, сроки, форма собрания и входные суммы проверяются;
- unit-, HTTP- и PostgreSQL-интеграционные тесты проходят;
- `go vet ./...` проходит;
- документация обновлена.
